# QuantX 买入/卖出计划独立领域新架构设计

> 状态：目标架构，待实施<br>
> 版本：1.0<br>
> 日期：2026-09-02<br>
> 适用范围：QuantX Windows Dev、个人单账户、A 股托管买入、自动退出和人工计划卖出

## 1. 结论

买入计划与卖出计划都不应依赖 `StrategyRun`。

目标结构为：

```text
EntryPlan                         ExitPlan
稳定买入计划、配置版本和状态       稳定卖出计划、规则、成本依据和状态
owner = ENTRY_PLAN               owner = EXIT_PLAN
        │                               ▲
        │ BUY TradeIntent               │ 真实 BUY fill 创建
        ▼                               │
公共意图/审批/OrderSizer/Risk/Capacity/订单/QMT 回报链
        │
        └──────────────► BucketLedger / Position / Audit

Engine 内：
EntryPlanRuntime                  ExitPlanRuntime
只负责调度，不是业务 owner         所有来源 ExitPlan 的唯一实时调度器
        │                               │
AshareManagedEntryPlanStrategy    AshareManagedExitPlanStrategy
.step(StrategyInput)              .step(StrategyInput)
```

其中：

- `EntryPlan` 本身就是一次不可复用的买入计划身份和 BUY owner，不再为每个配置版本创建
  `StrategyRun`；
- `ExitPlan` 本身就是 SELL owner，所有来源的退出计划都由公共 `ExitPlanRuntime` 调度；
- `source_execution_ref` 只回答“这个退出计划由哪次真实入场产生”，不决定谁负责运行 SELL；
- `EntryPlanRuntime` 和 `ExitPlanRuntime` 是唯一 Engine 进程内的应用调度器，不进入订单 owner，
  也不拥有账户余额、委托或成交真相；
- LIVE 与 BACKTEST 继续调用同一 `StrategyBase.step(StrategyInput)` 纯决策入口；移除的是
  `StrategyRun` 生命周期、外键和状态容器，不是策略接口；
- 现有 `ManagedEntryPlanEvaluator`、`ExitPlan/ExitPlanBook` 规则、授权、OrderSizer、风控、
  `AccountCapacityService`、durable outbox/inbox 和 QMT 回报收敛全部保留；
- 不保留一个泛化的 `ManagedPlan(kind=ENTRY/EXIT)` 超级聚合。买入与卖出的目标、状态机、
  更新规则和安全语义不同，应拥有各自的表、用例和 GraphQL 契约。

这个设计让“计划”回到真实业务语义：用户创建的是一项可暂停、可审计、可完成的交易计划，
而不是隐藏在策略运行实例中的一段参数和 `custom_state`。

## 2. 范围与术语

### 2.1 买入计划

买入计划回答：

- 买哪一个固定标的；
- 建仓到什么目标或追加多少金额/数量；
- 哪些价格、趋势或人工触发条件允许提出一笔 BUY；
- 如何分批、限额、冷却、过期和授权；
- 真实 BUY 成交后应创建什么冻结退出模板。

它不回答真实可买数量、最终价格是否合法、券商是否成交，也不拥有成交后退出状态机。

### 2.2 卖出计划

卖出计划统一称为 `ExitPlan`，回答：

- 保护哪一段真实持仓；
- 以什么冻结成本依据计算收益；
- 哪些规则触发卖出；
- 计划目标卖量和 T+1 策略；
- 自动或人工确认、价格保护和剩余数量如何推进。

它既可以由 EntryPlan、做 T 助手、打板助手或普通策略的真实 BUY fill 创建，也可以由用户针对
现有持仓手工创建。来源不同不应产生两套 SELL 状态机。

### 2.3 计划、配置版本与回放不是同一身份

- `plan_id`：一次真实业务计划的稳定且不可复用身份；
- `config_version_id`：该计划的一份不可变配置快照；
- `replay_id`：隔离历史回放身份，只引用冻结配置，不等于真实 plan；
- `intent_id/order_id/client_order_id`：公共执行链身份；
- `source_execution_ref`：ExitPlan 的入场来源引用。

不得再让一个 `run_id` 同时充当上述多种身份。

## 3. 当前实现评估

当前代码已经拥有大量应保留的正确基础：

- `ManagedEntryPlanConfig/State/Evaluator` 是无数据库、Broker 和网络依赖的纯领域模型；
- `managed_plans` 已把稳定 `plan_id` 与不可变配置版本从 `StrategyRun` 中初步分离；
- `entry_plan_authorization_*` 已有精确授权、消费和事件审计；
- `auto_exit_plans` 已是 PAPER/LIVE 退出状态的持久化真源，并有 `state_version` CAS；
- `ExitPlanMonitor` 已证明人工计划可以不创建 `StrategyRun`；
- 退出规则、成本依据、T+1、自动授权、零成交证明和 sticky error 语义已经成熟；
- 买入与卖出都能生成标准 `TradeIntent` 并经过统一执行链；
- 买入计划和退出计划都已有独立历史回放能力。

主要问题如下：

| 当前问题 | 实际影响 | 目标修正 |
|---|---|---|
| `managed_plans.current_run_id` 指向每个版本的 `StrategyRun` | 稳定 plan 仍无法独立运行、恢复和终结 | `EntryPlan` 自身成为 owner，状态直接持久化 |
| `managed_plan_config_revisions.run_id` 一对一绑定运行 | 配置版本被运行实现污染 | 版本只绑定 plan 和内容哈希 |
| 买入算法状态存于 `StrategyRunState.custom_state` | 计划真源被策略容器分裂 | 新增一对一 `entry_plan_states` |
| BUY intent 使用 `StrategyRunIntentOrigin/run_id` | 审批、订单和回报必须伪装成策略 | 使用 `ExecutionOwnerRef(ENTRY_PLAN, plan_id)` |
| 入场来源 ExitPlan 必须由原 StrategyRun 的热缓存执行 | 入场已完成后仍强迫来源运行长期存活 | 所有 ExitPlan 由统一 `ExitPlanRuntime` 执行 |
| `auto_exit_plans.strategy_run_id` 参与 owner 校验 | 人工与自动来源形成两条调度路径 | 保存 `source_execution_ref`，SELL owner 始终为 EXIT_PLAN |
| `ManagedPlan(kind=ENTRY/EXIT)` 同时包裹两类业务 | 两个状态机被错误统一，ExitPlan 又与 `auto_exit_plans` 重复 | 删除 EXIT wrapper，ENTRY 演进为专用聚合 |
| 回放生命周期依赖 StrategyRun/StrategyBacktest | 历史研究污染生产运行身份 | 使用专用 replay/version 真源和隔离 broker |

问题不在于策略接口本身，而在于 `StrategyRun` 被用作业务计划、配置版本、运行状态、执行 owner、
回放身份和退出调度器的共同容器。

## 4. 设计目标与非目标

### 4.1 目标

1. EntryPlan 和 ExitPlan 分别拥有唯一、清晰、可恢复的领域真源。
2. 新计划全链不再创建或写入 `StrategyRun/strategy_run_id`。
3. 买入、卖出、回放继续通过 `StrategyBase.step(StrategyInput)` 使用同一决策语义。
4. 配置、算法状态、意图、订单、成交和持仓归因各自只有一个权威来源。
5. 真实 BUY fill 才能创建或扩大 ExitPlan，BUY intent 和 `command_ack` 均不能。
6. ExitPlan 不依赖来源运行存活；来源仅用于审计、冲突检查和结果投影。
7. 编辑、暂停、取消、过期、重启和乱序回报都具有明确原子语义。
8. EntryPlan、做 T 和打板产生的 BUY 能复用同一个 ExitPlan 执行域。
9. PAPER、LIVE、BACKTEST 严格隔离，任何回放都不能进入 QMT 实盘路由。
10. 每次等待、少买、不买、拒绝、延迟、卖出和异常都能还原原因及输入快照。

### 4.2 非目标

- 不把买入计划做成通用工作流引擎或任意脚本执行器。
- 不合并 EntryPlan 和 ExitPlan 状态机。
- 不创建每个计划独立进程、QMT 会话、资金池或 Broker。
- 不新增第二套现金、持仓、可卖量、冻结量或订单真源。
- 不让策略或计划计算最终合法订单数量。
- 不在第一版给买入/卖出计划加入 ML 模型、自动调参或自然语言交易条件。
- 不让生成式 AI 直接改变计划配置、授权或订单。
- 不为旧运行保留长期双写、默认 owner 或 metadata 旁路。
- 不为了目录统一而强制打板助手或做 T 复用 EntryPlan 聚合。

## 5. 必须保持的交易边界

1. LIVE 与 BACKTEST 的行情决策调用同一个 `StrategyBase.step(StrategyInput)`。
2. 策略只输出 `TradeIntent[]`、计划命令和算法状态补丁，不访问账户、数据库、网络、文件或 QMT。
3. 策略不读取真实可用资金、冻结资金、真实可卖量，不计算最终合法数量。
4. A 股交易时段、T+1、涨跌停、停牌、整手、零股、资金和可卖量由统一交易域、OrderSizer、
   风控、Capacity 和 Broker 处理。
5. QMT Agent 是唯一 XTData/XTTrading 边界；成交只能由券商委托与成交回报推进。
6. `command_ack` 只表示投递或本地处理结果，不得推进计划成交状态。
7. 回报先进入 durable inbox，再由 Engine 串行、幂等收敛。
8. Redis 只负责唤醒和广播；PostgreSQL 是计划、意图、订单关联和审计真源。
9. 仓位归因继续使用 `locked_core/core/swing`，计划不是新仓位桶。
10. 所有 owner、配置、授权、意图、订单和回报关联都必须是强类型且可验证的持久字段。

## 6. 公共执行所有权

### 6.1 明确 owner 类型

在本设计与做 T、打板新架构同时落地后，公共类型为：

```text
ExecutionOwnerType =
  STRATEGY_RUN
  | T_ASSISTANT_EXECUTION
  | ENTRY_PLAN
  | BOARD_ASSISTANT_EXECUTION
  | EXIT_PLAN
  | MANUAL_COMMAND

ExecutionOwnerRef
  owner_type
  owner_id
```

语义如下：

| owner type | 拥有的业务命令 |
|---|---|
| `STRATEGY_RUN` | 真正普通策略实例产生的意图 |
| `T_ASSISTANT_EXECUTION` | 做 T 助手新 ENTRY |
| `ENTRY_PLAN` | 托管买入计划 BUY |
| `BOARD_ASSISTANT_EXECUTION` | 账户级打板助手 BUY |
| `EXIT_PLAN` | 任意来源退出计划 SELL |
| `MANUAL_COMMAND` | 不形成计划的明确人工一次性命令 |

不增加 `MANAGED_PLAN`、`ASSISTANT` 或 `AUTOMATION` 这类弱类型 owner。公共路由必须能仅凭
`owner_type + owner_id` 找到唯一领域记录并验证其环境、账户、状态和目标标的。

### 6.2 QMT 协议边界

`ExecutionOwnerRef` 只保留在服务端 durable intent、pending、correlation 和 outbox 中。
QMT Agent 的目标 1.2 命令只接收 `client_order_id` 和执行必需字段，不接收 plan、run、batch、
模型或业务 owner。回报由服务端持久 correlation 还原 owner。

不得把已删除字段塞入 `request_metadata` 形成第二套协议。owner 缺失、冲突或无法解析时必须
fail-closed，不能默认成 `STRATEGY_RUN`。

## 7. EntryPlan 领域

### 7.1 聚合身份

`EntryPlan` 同时是用户可见计划和 BUY 执行 owner：

```text
EntryPlan
  plan_id
  account_id
  instrument_code
  environment = PAPER | LIVE
  status
  current_config_version_id
  state_version
  created_at / activated_at / drain_requested_at / completed_at
```

一个 plan：

- 只属于一个账户和一个固定标的；
- 环境创建后不可在原地从 PAPER 改成 LIVE；切换环境要创建显式 successor plan；
- 终态后不可重新启用，重新执行必须创建新 plan id；
- 可以有多个不可变配置版本，但同一时刻只有一个 active version；
- 可以产生多笔分批 BUY，但同一时刻最多一个未收敛的 BUY intent/order；
- 真实 BUY fill 可以创建多个冻结 ExitPlan，不能把多个批次合并后改写历史成本。

同一账户、同一标的最多一个非终态 LIVE EntryPlan；需要改变目标或规则时编辑该计划，终态后再次
建仓则创建新 plan。PAPER 计划使用隔离模拟账户，不参与 LIVE 唯一性约束。

### 7.2 配置版本

```text
EntryPlanConfigVersion
  config_version_id
  plan_id / version
  schema_version
  canonical_payload / config_hash
  target_policy
  trigger_rules
  pacing_policy
  execution_policy
  completion_policy
  exit_plan_template?
  created_by / created_at
```

配置只允许由 typed command 规范化生成，不接受任意 JSON。版本必须包含当前
`ManagedEntryPlanConfig` 已有的完整语义：目标、baseline、规则、分批、价格上限、额度、授权、
过期和退出模板。

以下变化必须追加版本：

- 目标金额、目标仓位、追加数量或 baseline；
- 任一触发规则及参数；
- 分批、单笔/每日上限、冷却；
- PAPER/LIVE 之外的授权方式、价格保护或有效期；
- ExitPlan 模板。

存在未收敛 BUY intent、pending/outbox、结果未知命令或工作买单时禁止发布新版本。已有真实 BUY
fill 派生的 ExitPlan 使用成交时冻结的模板，不受后续 EntryPlan 配置修改影响。

### 7.3 状态

目标状态沿用已经成熟的领域语义：

```text
DRAFT
  -> ARMED / ACCUMULATING
  -> AWAITING_APPROVAL
  -> ENTRY_PENDING
  -> ACCUMULATING / COMPLETED

任意可运行状态 -> PAUSED
取消/过期且有未决命令 -> DRAINING
DRAINING -> CANCELLED / EXPIRED
不确定或矛盾事实 -> RECONCILE_REQUIRED / ERROR
```

核心状态持久化到一对一 `entry_plan_states`：

- 累计真实成交数量和金额；
- 当前 pending intent/stage/rule/activation；
- pending 请求量、真实成交量和结果水位；
- 每日订单数、每日成交额和冷却；
- 已完成 rule/activation；
- 有界的规则算法状态；
- terminal request 及原因；
- 最后 material 决策摘要和数据质量。

状态不能存真实账户余额、持仓总量、可卖量、Broker 订单副本或 ExitPlan 全量副本。

### 7.4 决策快照

每次评估构建不可变 `EntryPlanDecisionSnapshot`：

```text
EntryPlanDecisionSnapshot
  snapshot_id / decided_at / accepted_market_watermark
  execution_ref = ENTRY_PLAN / plan_id
  config_version_id / config_hash / state_version
  account_snapshot_version
  instrument_code
  quote + daily/completed-bar observations
  current position projection
  same-symbol pending BUY/SELL obligations
  account execution capability
  risk/liquidity planning caps
  manual trigger command?
```

账户和市场事实由 Engine 在调用策略前冻结。策略只接收满足点时因果约束的快照，并通过
`StrategyCadence.SNAPSHOT` 调用 `AshareManagedEntryPlanStrategy.step()`。不得让策略自己查询
Repository 或读取实时账户服务。

### 7.5 原子决策提交

一次 material 评估必须在同一事务中：

1. 锁定 `entry_plans/entry_plan_states` 并校验 config、state version 和 snapshot watermark；
2. 调用纯 `ManagedEntryPlanEvaluator`；
3. 写入有界状态补丁和 append-only `entry_plan_events`；
4. 若产生 BUY，写入同一稳定 ID 的 `TradeIntentRecord(owner=ENTRY_PLAN/plan_id)`；
5. 写入审批或自动授权所需的冻结指纹；
6. CAS 推进 state version；
7. 一次提交或整体回滚。

不能先把状态改成 `AWAITING_APPROVAL` 再异步补 intent，也不能先创建 intent 后丢失对应计划状态。

### 7.6 跨计划账户准入顺序

不同标的 EntryPlan 可能在同一时段同时触发。它们不共享一个业务 Coordinator，但必须经过账户级
`EntryPlanAdmissionSequencer`，避免事件循环先后决定谁抢到现金：

- AUTO-ready intent 按 `decision_time、plan_id、intent_id` 稳定排序；
- 人工确认 intent 按挑战实际消费时间和 intent id 排序；
- intent/outbox 保存 `admission_batch_id/admission_rank`；
- 每个 intent 仍在账户锁内读取最新 Capacity，前一笔受理后后一笔可以少买或拒绝；
- sequencer 不预留长期现金，也不保证 Broker 成交顺序。

这是公共账户准入的确定性排序，不把多个 EntryPlan 合并为一个账户级超级计划。

### 7.7 授权

`entry_plan_authorization_grants` 继续保留，但删除 `run_id` 外键，授权绑定：

```text
plan_id
config_version_id / config_hash
account_id / instrument_code / environment
subject_user_id / device_session_id
max_total_amount / max_single_amount / max_position_pct / max_buy_price
valid_from / expires_at
authorization_fingerprint
state_version lower bound
```

每笔 AUTO 消费必须与 intent、最终数量、受保护限价和账户快照一起原子记录。配置变化、暂停、
终态请求、账户安全状态变化或对账异常立即撤销授权。

人工确认绑定 exact intent、snapshot、config、state version 和 TTL；确认后仍要在账户锁内使用最新
行情、资金、仓位、Capacity 和 QMT 快照重新裁决。

## 8. ExitPlan 独立执行域

### 8.1 计划自身是 owner

所有 SELL intent 固定使用：

```text
execution_ref = EXIT_PLAN / plan_id
source_execution_ref = 原入场 owner；人工计划使用 MANUAL_COMMAND / creation_command_id
```

`source_execution_ref` 可为：

- `ENTRY_PLAN/plan_id`；
- `T_ASSISTANT_EXECUTION/execution_id`；
- `BOARD_ASSISTANT_EXECUTION/execution_id`；
- `STRATEGY_RUN/run_id`；
- `MANUAL_COMMAND/creation_command_id`。

它只能用于审计、来源策略约束、冲突检查和 UI 投影。SELL 的恢复、审批、订单和回报路由只依赖
`EXIT_PLAN/plan_id`。

### 8.2 唯一 `ExitPlanRuntime`

Engine 内只有一个账户级 `ExitPlanRuntime` 调度所有 PAPER/LIVE 活动计划：

```text
auto_exit_plans 权威行
  -> 按账户/标的/优先级选择到期计划
  -> 构建 ExitPlanDecisionSnapshot
  -> AshareManagedExitPlanStrategy.step(SNAPSHOT)
  -> 原子 state CAS + SELL TradeIntent
  -> 公共执行链
  -> QMT ORDER/TRADE inbox
  -> 原计划状态收敛
```

调度器本身不是 owner，不持久化第二份计划状态，也不把所有计划装入一个共享可变大对象。可以有
有界热缓存，但任何恢复和冲突裁决都重新读取 `auto_exit_plans`。

原 `ExitPlanMonitor` 演进为该 runtime，不再只扫描人工来源。来源运行不再保存或恢复 PAPER/LIVE
`ExitPlanBook`；`ExitPlanBook([plan])` 只作为纯规则执行器或回测内存结构使用。

### 8.3 计划真源

保留 `auto_exit_plans` 作为当前物理表，避免只为名称做高风险迁移；应用/domain 类型统一称为
`ExitPlanRecord`。目标字段包括：

```text
plan_id / account_id / instrument_code / environment
source_owner_type / source_owner_id / source_business_id
source_config_version / source_fill_ids
bucket / protected_volume / filled_exit_volume / remaining_volume
cost_basis_snapshot
template_snapshot / config_version / state_version
status / pending_intent_id / result_watermark
exact auto authorization envelope?
created_at / activated_at / completed_at
```

删除 `strategy_run_id` 的所有权语义。存量普通策略来源迁移为
`source_owner_type=STRATEGY_RUN, source_owner_id=旧 run_id`，但 ExitPlan 自己仍是 SELL owner。

### 8.4 创建与扩大

只有 durable、去重后的真实 BUY `TradeExecutionEvent` 可以创建或扩大 ExitPlan。事务必须同时验证：

- BUY fill 的 intent、order、correlation 和 source owner 一致；
- 模板、最大保护量和授权信封来自该 BUY 的冻结证据；
- 相同 fill identity 未处理；
- bucket、账户、标的和 source owner 不冲突；
- 成本依据由真实 fill 和费用政策冻结。

一个分批 BUY 默认产生一个确定性 plan id；只有模板显式声明可合并且成本/授权语义一致时才允许
扩大同一 plan。不得为了 UI 简洁自动混合不同成本依据。

### 8.5 退出评估快照

`ExitPlanDecisionSnapshot` 至少包含：

- plan/config/state identity；
- 最新已接受行情及 freshness；
- 冻结成本、峰值、动态底线和规则状态；
- 计划剩余量与当前真实持仓/可卖量投影；
- same-symbol 其他 ExitPlan 的认领和工作 SELL；
- T+1、涨跌停、停牌和账户减仓能力；
- Broker/QMT 对账水位。

策略只判断规则是否触发并给出目标计划卖量，最终合法数量仍由 OrderSizer、T+1、风控和 Capacity
决定。

### 8.6 来源生命周期独立

入场 owner 停止新 BUY 后，只需完成它自己尚未收敛的 BUY intent、pending/outbox 和结果未知命令。
已经激活的 ExitPlan 由自身 runtime 继续执行；来源 owner 可以进入终态，但记录不得硬删除。

因此：

- EntryPlan 完成建仓后可以 `COMPLETED`，不必等待所有退出卖完；
- 做 T 或打板 execution 可以在自己的 ENTRY 义务归零后停止；
- UI 仍通过 `source_execution_ref` 展示下游未完成 ExitPlan；
- 新 owner 的账户协调器必须读取全账户 active ExitPlan 和工作订单，不能只看自己的运行内存。

这消除了“为了卖出而让入场运行永不停止”的隐性生命周期耦合。

### 8.7 同标的多计划冲突

`ExitPlanRuntime` 必须复用现有 `lock_exit_plan_scope/LockedExitPlanScope` 和持久保护量认领，
不能因为统一调度而让多个 plan 同时认为自己可以卖出同一批股票：

- 每个 plan 的 protected/remaining volume 在创建时冻结，禁止跨 plan 自动借用或重分配；
- 同标的多个规则同时触发时，按规则优先级、计划创建时间和 plan id 稳定排序进入账户锁；
- 每个 SELL 在最终受理时重验当前持仓、可卖量、工作 SELL 和全部计划认领；
- 若外部成交导致总认领大于真实持仓，相关计划进入 `RECONCILE_REQUIRED`，不得猜测缩减哪一个；
- 一个 plan 的 partial fill 只推进自己的剩余量，不修改其他 plan；
- 结果未知 SELL 保持占用，不能让后续 plan 以新 intent 绕过。

## 9. 用户命令语义

### 9.1 创建 EntryPlan

创建命令必须包含不超过 128 字符的业务幂等键。单事务完成：

1. 规范化 typed config；
2. 冻结 baseline 与账户快照版本；
3. 创建 `entry_plans`、config v1、初始 state 和事件；
4. 若请求启用，校验环境和授权后进入 `ARMED`；
5. 不创建 StrategyRun。

同键重试只返回原计划；同键不同 payload 拒绝。

### 9.2 编辑 EntryPlan

编辑要求 expected config/state version。存在结果未知 BUY 时拒绝；否则：

1. 追加不可变 config version；
2. 根据显式 `state_migration_policy` 保留、重置或重算允许的算法状态；
3. 切换 head；
4. 撤销旧自动授权和未消费人工挑战；
5. 追加事件。

不能通过创建新运行来隐藏失败的编辑，也不能让两个配置版本并行产生 BUY。

### 9.3 暂停、取消与过期

- `PAUSE`：阻止新决策和新 intent，不取消已经越过 Broker 边界的订单；
- `CANCEL/EXPIRE`：先持久 terminal request；若有未决 BUY 则进入 DRAINING；
- 从未投递的本地命令可按权威零成交证明取消；已投递结果未知只能 reconcile；
- 终态只在所有自身 BUY 义务收敛后进入；下游 ExitPlan 不阻止终态。

### 9.4 人工 ExitPlan 与清仓

人工计划、动态止盈和清仓继续直接创建 `ExitPlan`，无需先创建 EntryPlan 或 StrategyRun。
批量清仓以 `group_id` 关联多个独立 plan；每个 plan 仍拥有自己的状态、授权和 SELL intent。

冲突认领、`AVAILABLE_NOW/UNTIL_SNAPSHOT_CLEARED`、成本依据、零成交证明和 sticky 隔离等现有安全
语义全部保留。

## 10. 决策与执行顺序

### 10.1 EntryPlan

```text
行情/人工命令唤醒
  -> 构建因果快照
  -> 锁 plan/state 并校验版本
  -> StrategyBase.step
  -> 原子状态 + BUY intent
  -> 人工确认或精确 AUTO grant
  -> 最新事实重验
  -> OrderSizer / Risk / AccountCapacityService
  -> pending / correlation / outbox
  -> QMT
  -> ORDER/TRADE inbox
  -> EntryPlan state + BucketLedger
  -> 真实 fill 创建 ExitPlan
```

### 10.2 ExitPlan

```text
行情/时间/回报唤醒
  -> 选择活动 plan
  -> 构建因果快照
  -> 锁 plan 并校验 state version
  -> StrategyBase.step
  -> 原子状态 + SELL intent
  -> 授权/最新事实重验
  -> OrderSizer / T+1 / Risk / Capacity
  -> pending / correlation / outbox
  -> QMT
  -> ORDER/TRADE inbox
  -> ExitPlan + BucketLedger 收敛
```

任何阶段失败都必须保持原 owner 和 intent identity，不能通过生成新 intent 或新 plan 绕过结果不确定。

## 11. 并发、锁与恢复

### 11.1 串行边界

- 同一 EntryPlan 的状态与 BUY 决策严格串行；
- 同一 ExitPlan 的规则、pending 和成交严格串行；
- 同账户最终容量受理严格串行；
- 同一 Broker command 的投递和回报收敛按稳定 identity 幂等；
- 不同账户不存在，本项目不增加账户路由抽象。

### 11.2 必须原子完成的事务

- plan state patch + material event + TradeIntent；
- 人工挑战消费 + pending/correlation/outbox 创建；
- AUTO grant 消费 + 最终准入；
- BUY fill 收敛 + BucketLedger + ExitPlan 创建/扩大；
- SELL fill 收敛 + ExitPlan 剩余量 + BucketLedger；
- terminal request + 新 intent 阻断；
- owner migration cutover marker + legacy producer disable。

### 11.3 重启恢复

Engine 启动顺序：

1. 获取 Engine 单实例租约；
2. 完成 owner/协议版本预检；
3. 恢复 durable inbox/outbox 和结果未知命令；
4. 恢复 EntryPlan 与 ExitPlan 权威状态；
5. 对 active plan 做 owner、config、state 和订单一致性审计；
6. 不一致计划进入 `RECONCILE_REQUIRED`；
7. 恢复调度，先处理退出和减仓，再允许新 BUY。

不得从 Redis、内存 Strategy 对象或 `StrategyRunState` 恢复计划真相。

## 12. 回放与回测

### 12.1 EntryPlan 回放

`entry_plan_replay_versions` 保存：

- `replay_id`、source plan/config snapshot；
- 环境固定 BACKTEST；
- 起始账户、持仓和 baseline；
- 数据 manifest/hash/coverage；
- 费用、滑点和 Broker 情景；
- 状态、进度、结果和失败证据。

回放创建隔离的模拟 EntryPlan identity，调用同一个
`AshareManagedEntryPlanStrategy.step(StrategyInput)`、OrderSizer、风险和 BacktestBroker；不写
真实 `entry_plans`、授权或 QMT outbox。

### 12.2 ExitPlan 回放

现有 `exit_plan_replay_projections` 可继续作为结果真源，但生命周期不再依赖 StrategyRun 或
StrategyBacktest。每个 replay 冻结 plan 模板、成本依据、起始数量、数据 manifest 和 Broker 情景，
调用同一个 `AshareManagedExitPlanStrategy.step()`。

回放中的模拟 ExitPlan 使用隔离 identity 和 BACKTEST namespace，不修改真实 plan 的 config、state、
授权或事件。

### 12.3 因果与数据质量

- 所有特征和规则输入的 as-of 不得晚于决策时点；
- 缺失 Tick、盘口、涨跌停、交易状态或成本数据只能阻断/保守降级；
- 新意图不能成交在产生它的同一条行情上；
- 回放窗口末不强制伪造成交或清仓；
- 真实历史 SELL 只作为参考，不篡改模拟路径。

## 13. 持久化真源

| 事实 | 目标真源 | 说明 |
|---|---|---|
| EntryPlan identity/head | `entry_plans` | 从 `managed_plans(kind=ENTRY)` 原子演进 |
| EntryPlan config | `entry_plan_config_versions` | append-only typed snapshot |
| EntryPlan mutable state | `entry_plan_states` | 一对一、CAS、核心字段 typed |
| EntryPlan events | `entry_plan_events` | material append-only |
| Entry AUTO grants | `entry_plan_authorization_*` | 删除 run 外键，绑定 plan/config |
| ExitPlan | `auto_exit_plans` | 保留物理表，领域名统一 ExitPlan |
| ExitPlan events | `auto_exit_plan_events` | 继续 append-only |
| BUY/SELL intent | 公共 `trade_intents` | owner ref，不再要求 run id |
| 账户准入排序 | `trade_intents` + `entry_plan_events` | 保存 admission batch/rank/结果，不另建现金真源 |
| pending/correlation/outbox/inbox | 公共执行表 | owner ref + stable business keys |
| 仓位与批次 | `BucketLedger` 等权威表 | 计划只引用，不复制 |
| Entry replay | `entry_plan_replay_versions` | 独立 BACKTEST identity |
| Exit replay | `exit_plan_replay_projections` | 去除 StrategyRun 生命周期依赖 |

`managed_plans(kind=EXIT)` 和 `managed_plan_config_revisions.run_id` 在迁移完成后删除；不得与新表长期双写。

## 14. GraphQL 与 UI

### 14.1 API 身份

买入页面只暴露 `planId/configVersion/status/stateVersion`，不再返回或接受 `strategyRunId`。
卖出页面暴露 `exitPlanId/sourceExecutionRef/configVersion/stateVersion`。

命令使用业务幂等键和 expected version，不能让客户端生成内部 order/correlation identity。

### 14.2 状态语义

UI 必须区分：

- 系统健康；
- 账户执行能力；
- plan 业务状态；
- 当前条件是否匹配；
- intent 是否待确认；
- 订单是否已投递；
- Broker 是否委托/成交；
- 下游 ExitPlan 是否仍活动。

不得把“计划运行中”“条件已匹配”“已批准”和“已成交”用一个绿色状态表达。

EntryPlan 完成后仍可显示其来源 ExitPlan，但页面文案应为“买入计划已完成，仍有 N 个独立退出计划”，
不能把计划伪装为仍在运行。

## 16. 迁移路线

### 阶段 0：冻结 StrategyRun 计划扩展

- 除安全修复外，不再向 StrategyRun、StrategyRunState 或 StrategyExecutor 增加 Entry/Exit 专用字段；
- 清点全部活动 managed plan、run、授权、pending、outbox、订单、ExitPlan 和 replay；
- 建立 owner/run/plan/intent/order/correlation 一致性审计；
- 固定当前 EntryPlan 与 ExitPlan 领域测试作为迁移基线。

### 阶段 1：完成公共 owner 与协议 1.2

- 落地 `ENTRY_PLAN` 与 `BOARD_ASSISTANT_EXECUTION` owner 类型；
- 公共 intent、approval、pending、correlation、outbox 和 report routing 改用 owner ref；
- 安全排空 protocol 1.1 未投递和结果未知命令后原子切换 1.2；
- 普通策略通过 adapter 保持 `STRATEGY_RUN` 行为。

### 阶段 2：建立 EntryPlan 真源

- 新增 `entry_plans/config_versions/states/events`；
- 将 `managed_plans(kind=ENTRY)`、当前 revision 和 StrategyRunState 规范化导入；
- 相同 plan/config/state 的 shadow evaluator 与旧运行逐事件比对；
- 授权表删除 run FK 并改绑 plan/config。

### 阶段 3：建立统一 ExitPlanRuntime

- `auto_exit_plans` 增加强类型 source execution ref 和 environment；
- 对所有活动计划完成 source、状态、pending、订单和授权审计；
- 新 runtime 在影子模式计算触发结果，不生成 SELL；
- 与现有来源 StrategyRun/人工计划 Monitor 逐行情比较。

### 阶段 4：EntryPlan 切换

- 对没有未决 BUY 的 plan，在同一切换事务禁用旧 run producer、启用新 plan runtime；
- 有 pending/outbox/结果未知订单的旧 run 只允许 DRAINING，禁止新 BUY；
- 未决义务归零后导入最终状态再切换；不复制、不改挂、不重发旧命令；
- 新 BUY owner 只允许 `ENTRY_PLAN`。

### 阶段 5：ExitPlan 切换

- 先用数据库租约/切换标记阻断所有旧退出 evaluator；
- 确认同一 plan 没有两个执行者后启用统一 ExitPlanRuntime；
- 已在途 SELL 保留 `EXIT_PLAN/plan_id` 和原 correlation，不重建 intent；
- 来源 run 可以在自身 BUY 义务归零后终结；
- 删除 PAPER/LIVE `ExitPlanBook` 热缓存恢复和人工计划/入场来源双路径。

### 阶段 6：回放切换与清理

- Entry/Exit replay 使用独立持久生命周期，不再创建 StrategyRun；
- 历史 StrategyRun replay 只读保留，不改写身份；
- 删除 `ManagedPlanRuntimeService`、`managed_plans(kind=EXIT)`、current_run_id、revision.run_id、
  plan-specific StrategyRun 字段和 legacy fallback；
- 更新当前卖出契约的 owner/运行章节为唯一新设计。

## 17. 测试要求

### 17.1 EntryPlan 领域

- target gap、pending exposure、baseline、分批与上限；
- 规则优先级、once、价格阶梯、趋势回撤和人工触发；
- 未来数据、价格上限、过期、冷却和每日限制；
- state patch 与 intent ID 确定性；
- 配置版本编辑和 state migration。

### 17.2 ExitPlan 领域

- 规则优先级、成本、峰值、动态底线、分批和 T+1；
- partial fill、乱序 ORDER/TRADE、zero-fill 证明与迟到反证；
- sticky ERROR、reconcile、授权撤销和持仓冲突；
- 不同 source owner 产生完全相同的 SELL owner/runtime 语义。

### 17.3 应用与并发

- plan state + intent 原子提交；
- 同 plan 并发 tick/command 只能成功一次；
- config/state expected version 冲突；
- 同账户同标的最多一个非终态 LIVE EntryPlan，PAPER namespace 不参与抢占；
- `EntryPlanAdmissionSequencer` 在并发触发和重放下保持稳定顺序，后一计划读取前一受理后的容量；
- 人工挑战消费与 outbox 原子性；
- AUTO grant 单调消费；
- BUY fill 与 ExitPlan 创建幂等；
- 来源 owner 终态后 ExitPlan 继续运行；
- Engine 重启、租约争用和 runtime 双执行防护。

### 17.4 迁移

- 活动旧 run 无 pending 时无损导入；
- 结果未知旧命令不改挂、不复制、不重发；
- 新路径没有伪造 strategy_run_id；
- legacy source plan 在统一 ExitPlanRuntime 下保持原 plan/intent/order identity；
- 旧义务归零后无双写、无 fallback、无孤儿授权。

### 17.5 回放

- LIVE/BACKTEST 同一 StrategyBase.step；
- 数据 manifest、因果顺序和同 tick 禁止成交；
- 费用、T+1、涨跌停、停牌、盘口限量和窗口末开放仓位；
- replay 不写实盘 plan、授权、outbox 或 QMT 命令。

## 18. 上线验收

必须同时满足：

1. 创建、编辑、运行、暂停和取消 EntryPlan 不创建 StrategyRun。
2. EntryPlan BUY 全链 owner 为 `ENTRY_PLAN/plan_id`，无 metadata owner 或默认 run fallback。
3. 所有来源 ExitPlan SELL 全链 owner 为 `EXIT_PLAN/plan_id`。
4. `source_execution_ref` 不参与 SELL runtime 选择，来源终态后退出仍可恢复。
5. PAPER/LIVE 计划状态不从 StrategyRunState 或内存 ExitPlanBook 恢复。
6. 配置、状态、intent 和事件在 material 决策中原子提交。
7. 真实 BUY fill 才创建 ExitPlan，ACK、intent 或委托接受均不能。
8. 最终数量、资金、T+1、涨跌停和停牌仍由公共执行链裁决。
9. Entry/Exit replay 不依赖 StrategyRun 且不接入 QMT。
10. protocol 1.2、乱序回报、重启恢复和结果未知命令测试通过。
11. 旧计划与运行义务全部排空，plan-specific StrategyRun 路径和双写已删除。
12. 买入/卖出执行健康 UI 不再暴露 run 作为计划身份。
13. 数据库约束和用例同时保证同账户同标的最多一个非终态 LIVE EntryPlan。
14. 多个 EntryPlan 同时触发时，准入 batch/rank、容量变化和拒绝原因可重放且不由抢锁顺序决定。

## 19. 与其他新领域的复用边界

| 公共能力 | EntryPlan 独有 | ExitPlan 独有 | 做 T/打板不得复用的部分 |
|---|---|---|---|
| `ExecutionOwnerRef` | target、trigger、pacing | trigger、sizing、T+1 | 不复用 EntryPlan 聚合 |
| `StrategyBase.step` 契约 | Entry snapshot/state | Exit snapshot/state | 各自 typed input |
| TradeIntent/审批/执行链 | BUY 授权 | SELL 授权 | 不共享业务状态枚举 |
| Capacity/outbox/inbox/QMT | 分批准入 | 持仓认领与减仓 | 不共享账户缓存 |
| BucketLedger/Position | baseline 和累计 fill | 成本与剩余保护量 | 不复制持仓真源 |
| ExitPlanRuntime | 只创建 source ref | 自身执行 owner | 做 T/打板不内嵌 SELL FSM |
| 回放基础设施 | Entry replay spec | Exit replay spec | 数据集与指标各自定义 |

买入计划当前没有已验证的模型需求，因此不接入空泛 scorer 或 model binding。若未来出现明确的
买点模型，应先定义 EntryPlan 专用标签、点时数据和发布门禁，再复用公共 model-ops；不能把做 T
或首板模型直接塞入计划条件。

## 20. 最终判断

最合理的边界不是“用新的运行表替换 StrategyRun”，而是让真实领域对象承担真实生命周期：

- EntryPlan 拥有买入配置、状态和 BUY；
- ExitPlan 拥有退出规则、状态和 SELL；
- 公共执行链拥有最终合法订单与可靠投递；
- QMT 回报拥有委托和成交事实；
- BucketLedger/Position 拥有仓位真相；
- StrategyBase 只保留纯决策边界。

这样既去掉了 `StrategyRun` 的错误依赖，也没有重新制造一个名为 `PlanExecution` 的通用运行壳。
做 T、买入计划和打板助手可以安全共享 ExitPlan 与执行基础设施，同时仍保持各自独立、强类型、
可审计的领域模型。
