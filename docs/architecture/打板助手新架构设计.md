# QuantX 打板助手独立领域新架构设计

> 状态：目标架构，待实施<br>
> 版本：1.0<br>
> 日期：2026-09-02<br>
> 适用范围：QuantX Windows Dev、个人单账户、A 股账户级首板/打板助手

## 1. 结论

账户级打板助手不应依赖 `StrategyRun`，也不应回退为“一只候选创建一个策略实例”。

目标结构为：

```text
一个账户级 BoardAssistantConfig
             +
一个可产生实盘 BUY 的 LIVE BoardAssistantExecution
             +
隔离的 PAPER/BACKTEST execution
             +
全市场 LimitUpRadar / FirstBoard feature source
             +
每标的 BoardCandidateState + 一个 BoardPortfolioCoordinator
             +
公共审批、OrderSizer、Risk、AccountCapacity、订单、ExitPlan 和 QMT 回报链
```

其中：

- `BoardAssistantConfig` 是用户意图和版本 head；
- `BoardAssistantExecution` 是一次可恢复、冻结配置和模型 binding 的业务执行 owner；
- BUY intent 使用 `ExecutionOwnerRef(BOARD_ASSISTANT_EXECUTION, execution_id)`；
- 真实 BUY fill 创建独立 `ExitPlan`，之后 SELL owner 固定为 `EXIT_PLAN/plan_id`；
- `LimitUpRadar` 只是点时市场发现输入，不是交易 owner，也不直接启动运行或下单；
- `AshareLimitUpBoardAssistantStrategy.step(StrategyInput)` 保留为 LIVE/BACKTEST 共用的纯决策入口，
  但不再把状态写入 `StrategyRunState`；
- `FirstBoardPromotion` 模型只负责候选质量估计和跨标的排序证据，不负责资格、授权、仓位或下单；
- 当前固定系数 `FirstBoardPromotionEvaluator` 视为可解释规则基线/SHADOW 对照，不冒充经过训练、
  校准和安全制品发布的 ACTIVE 模型；
- 模型训练复用 QuantX 已实现的不可变数据集、DEVELOPMENT/FINAL、Worker、GPU 资格、安全制品和
  发布门禁能力，但拥有打板专用数据、标签、指标、注册表和 runtime binding。

打板助手与多标的做 T 都是“动态 Universe + 多候选竞争 + 账户统一准入”，但二者不能共享执行聚合：
做 T 围绕已有持仓和正向 T+1 置换，打板围绕首板候选、人工确认、扫板价格与隔夜尾损。它们只共享
稳定公共执行地基和模型运维原语。

## 2. 设计目标与非目标

### 2.1 目标

1. 全市场候选在同一因果快照中完成资格、评分、排名和账户预算分配。
2. 每个标的的雷达阶段、尝试、pending、冷却和审计状态相互隔离。
3. 配置、执行、候选状态、模型分数和回放结果不再以 StrategyRun 为真源。
4. 人工偏好、人工布防和交易授权严格分离；`PREFER/ARMED` 不能绕过门禁。
5. 同一账户同一时刻最多一个 execution 可以产生真实打板 BUY。
6. 真实 BUY 成交后统一进入独立 ExitPlan 域，不在助手中复制 SELL 状态机。
7. 规则、模型、排序、确认、容量和 Broker 事实拥有不同状态与原因码。
8. PAPER/LIVE/BACKTEST 使用同一策略 step、同一候选协调和同一执行重验语义。
9. 回放使用共享账户、历史雷达帧和保守盘口成交，不把多只股票结果简单相加。
10. 模型的训练、注册、发布、绑定、推理和失效都可审计且 fail-closed。

### 2.2 非目标

- 不恢复全市场“一票一 StrategyRun”。
- 不支持多账户、多租户或多 QMT 会话。
- 不模拟无法验证的封板排队优先级。
- 不让 Radar、模型、AI 研究任务或前端直接下单。
- 不让模型决定股票是否停牌/ST/退市风险、最终数量、订单类型或追价。
- 不把做 T 的 `TAssistantExecution/TTradingEnvelope/PortfolioTCoordinator` 复用于打板。
- 不新建第二套现金、仓位、订单、Reservation 或 SELL FSM。
- 不在第一阶段启用无人值守 LIVE AUTO 买入；实盘固定人工确认。
- 不在第一版引入在线学习、深度学习、强化学习或逐 Tick 远程模型服务。
- 不把生成式 AI 研究摘要作为特征、标签、门禁或授权证据。
- 不为旧 StrategyRun 保留长期兼容 owner、双状态或 fallback。

## 3. 必须保持的 QuantX 边界

1. LIVE 与 BACKTEST 都调用 `StrategyBase.step(StrategyInput)`。
2. 策略只输出 `TradeIntent[]` 和算法状态补丁，不访问数据库、账户、网络、文件或 QMT。
3. 策略不计算最终合法数量，不读取真实可用现金、冻结资金和 Broker 可用量。
4. A 股交易时段、涨跌停、停牌、整手、资金、T+1 和最终可卖量由公共交易域处理。
5. QMT Agent 是唯一 XTData/XTTrading 边界；真实成交只来自其 ORDER/TRADE 回报。
6. `command_ack` 不得推进持仓、ExitPlan 或候选成交状态。
7. 回报先持久化 inbox，再由 Engine 串行、幂等收敛。
8. PostgreSQL 是状态真源；Redis 只用于唤醒和广播。
9. 打板买入固定进入 `swing`，不新增仓位 bucket。
10. 任何候选淘汰、确认失效、少买、拒单、无成交和模型阻断都必须有稳定原因码。

## 4. 当前实现评估

当前实现已经具备值得保留的能力：

- Engine 账户级 `LimitUpBoardAssistantService` 和唯一配置行；
- 全市场 `LimitUpRadar`、点时首板评估、候选偏好和日内布防；
- 纯 `select_limit_up_board_universe()` Top-N 选择；
- `AshareLimitUpBoardAssistantStrategy` 的固定人工确认与执行前价格重验；
- 首板规则、涨停价、最小价位、一字板、ST/退市和数据质量门禁；
- 单标的状态、pending 防重复、确定性 ExitPlan 模板；
- `FirstBoardPromotionStudy` 的交易日 walk-forward、分板块模型、Bootstrap 和 CVaR 证据；
- `FirstBoardModelRelease` 的 SHADOW/PAPER/LIVE 初步门禁；
- 共享账户、历史雷达帧、四种成交情景和五档盘口的助手回放；
- durable candidate preference、research job/artifact 和 UI projection。

当前耦合与缺口：

| 当前问题 | 影响 | 目标修正 |
|---|---|---|
| `limit_up_board_assistant_configs.strategy_run_id` | 配置 head 同时承担运行指针 | 独立 config version + BoardAssistantExecution |
| Engine 通过 StrategyManager 创建、接续和停止助手 | 账户级助手伪装为策略实例 | 专用 BoardAssistantRuntime |
| Universe 状态写入 `StrategyRunState.instrument_states` | 大 JSON、局部 CAS 和恢复边界不清 | 独立 BoardCandidateState/DecisionCycle |
| intent/run/approval/ExitPlan 以 run_id 串联 | 所有公共链被 StrategyRun 外键绑住 | owner=`BOARD_ASSISTANT_EXECUTION` |
| 退出计划保存在来源运行热缓存 | 助手停用后仍必须保留运行 | 公共 ExitPlanRuntime 独立执行 |
| `promotion_model_mode=SHADOW/PAPER/LIVE` | 模型阶段与交易环境混为一轴 | scorer mode、registry stage、environment 三轴分离 |
| 固定系数 evaluator 自称 model version | 无训练 artifact、校准或 runtime self-test | 降为 RULE_BASELINE/SHADOW control |
| release 表只有汇总门禁 | 数据/spec/artifact/hash 不可完整追溯 | 复用不可变训练与发布基础设施 |
| Radar item 直接携带 position/liquidity cap | 市场发现与账户规划混合 | Radar 只给市场事实，Coordinator 计算预算上限 |
| 当前 replay 最终仍依赖 StrategyRun | 回放身份污染生产运行 | BACKTEST BoardAssistantExecution |

## 5. 目标逻辑架构

```text
XTData whole quote / daily facts
             │
             ▼
      LimitUpRadarSource
只生成点时市场候选帧，不读账户、不下单
             │
             ▼
BoardDecisionSnapshotBuilder
冻结 radar frame、完整分钟、最新 Tick、配置/模型/账户水位
             │
             ▼
BoardAssistantRuntime
加载 BoardAssistantExecution 和每标的状态
             │
             ▼
AshareLimitUpBoardAssistantStrategy.step(SNAPSHOT)
纯规则资格 + 候选提案 + 状态补丁
             │
             ├────────► BoardModelScorer（可选 SHADOW/ACTIVE）
             │
             ▼
BoardPortfolioCoordinator
稳定排序、预算上限、并发与行业约束
             │
             ▼
持久 TradeIntent(owner=BOARD_ASSISTANT_EXECUTION)
             │
             ▼
人工确认 + EntryExecutionGate 最新事实重验
             │
             ▼
OrderSizer / Risk / AccountCapacity / outbox / QMT
             │
             ▼
真实 BUY fill -> BucketLedger + ExitPlan(source_execution_ref)
                                      │
                                      ▼
                               公共 ExitPlanRuntime
```

物理部署仍保持 API、Engine、Worker、QMT Agent 的现有边界。逐行情规则、批量 CPU 推理、候选协调、
审批恢复和订单路由都在唯一活跃 Engine 内；Worker 只承担离线数据、训练和评估。

## 6. 配置与执行身份

### 6.1 BoardAssistantConfig

现有单账户配置演进为 head + append-only version：

```text
BoardAssistantConfigHead
  config_id / account_id / state_version
  enabled
  desired_environment = PAPER | LIVE
  active_config_version_id

BoardAssistantConfigVersion
  config_version_id / config_id / version
  schema_version / canonical_payload / config_hash
  universe_policy
  entry_rule_policy
  portfolio_policy
  entry_execution_gate_policy
  exit_plan_template_policy
  scorer_mode = RULE_ONLY | SHADOW | ACTIVE
  model_runtime_binding?
  created_at
```

配置版本保存当前设置的完整 typed 快照，包括候选数量、时间窗、涨停距离、风险预算、流动性、人工
确认 TTL、委托 TTL、价格偏离、退出模板和 scorer 选择。

删除：

- `strategy_run_id`；
- 把 config version 当作可变 settings JSON revision 的做法；
- `auto_exit_acknowledged` 作为实盘授权。一个布尔确认不能替代设备绑定、计划级精确授权。

### 6.2 BoardAssistantExecution

```text
BoardAssistantExecution
  execution_id
  config_id / config_version_id / config_hash
  account_id
  environment = PAPER | LIVE | BACKTEST
  entry_authorization = MANUAL_CONFIRM
  status = CREATED | WARMING | RUNNING | DRAINING
           | STOPPED | FAILED | RECONCILE_REQUIRED
  rule_policy_version / feature_schema_version
  scorer_mode / model_runtime_binding?
  universe_revision
  last_assigned_cycle_sequence / last_committed_cycle_sequence
  started_at / drain_requested_at / completed_at
  state_version
```

一个 LIVE execution 冻结配置、规则、模型和退出模板。配置、scorer mode 或任何 model binding
变化时都创建 successor；不能在运行中原地替换 artifact。

个人单账户最多一个 execution 可产生真实 BUY。PAPER/BACKTEST 可并存，但必须使用隔离的 intent、
order、broker 和 projection namespace。

### 6.3 三条独立轴

| 轴 | 状态 | 回答的问题 |
|---|---|---|
| execution environment | PAPER / LIVE / BACKTEST | 订单进入哪里 |
| entry authorization | MANUAL_CONFIRM | BUY 是否需要用户确认 |
| scorer mode | RULE_ONLY / SHADOW / ACTIVE | 模型是否计算、是否影响排序 |

模型 `SHADOW` 不等于 PAPER，模型 `ACTIVE` 也不等于允许 LIVE AUTO。第一阶段实盘始终人工确认。
`RULE_ONLY` 无 binding；`SHADOW` 只能绑定 registry `SHADOW`，模型结果仅作旁路证据；`ACTIVE`
只能绑定唯一 registry `ACTIVE`，其合法分数才可进入真实排名。

## 7. ExecutionOwnerRef

打板 BUY 使用：

```text
ExecutionOwnerRef(
  owner_type = BOARD_ASSISTANT_EXECUTION,
  owner_id = execution_id,
)
```

公共 owner 枚举与买入/卖出计划、做 T 设计保持一致：

```text
STRATEGY_RUN
T_ASSISTANT_EXECUTION
ENTRY_PLAN
BOARD_ASSISTANT_EXECUTION
EXIT_PLAN
MANUAL_COMMAND
```

`TradeIntent`、审批、pending、correlation 和 outbox 保存 owner ref。QMT protocol 1.2 不发送业务 owner，
只发送 `client_order_id` 和执行必需字段；服务端以 durable correlation 还原。

不得用 `metadata.strategy_run_id`、`request_metadata.owner` 或假的 run id 保留旧路径。

## 8. Radar、Universe 与人工偏好

### 8.1 Radar 只拥有市场发现

`LimitUpRadarSource` 输出不可变点时帧：

```text
LimitUpRadarFrame
  frame_id / trade_date / observed_at
  source_max_at / market_watermark
  feature_schema_version
  items[]
  frame_hash / quality
```

每个 item 只包含截至 `observed_at` 可见的市场、证券、板块和数据质量事实。不得包含当前账户现金、
持仓上限、目标下单金额或最终授权状态。

### 8.2 Universe 选择

纯 `BoardUniverseSelector` 根据：

- 雷达规则资格；
- config 的阶段、时间窗和 Top-N；
- 用户 `PREFER/IGNORE`；
- 日内 `ARMED/DISARMED`；
- predecessor 未决 BUY 的 sticky symbol；

输出当次 execution 的候选集合和逐票原因。选择器不读取时钟、数据库或账户服务；调用方把冻结输入
显式传入。

### 8.3 偏好不是授权

- `PREFER`：只在同等硬门禁下提高候选排序优先级；
- `IGNORE`：当日排除新候选；
- `ARMED`：允许该票进入候选池，不能跳过规则、模型、排名、确认或风控；
- `DISARMED`：阻止新的 candidate，不取消已越过 Broker 边界的命令。

偏好和布防记录保持 `(account_id, trade_date, instrument_code)` 唯一，并有 actor、业务幂等键和单调
version。它们不是 execution owner。

## 9. 候选状态与决策周期

### 9.1 BoardCandidateState

每个 execution + symbol 一行：

```text
BoardCandidateState
  execution_id / instrument_code
  state_version
  radar_stage / eligibility / reason
  last_frame_id / last_market_watermark
  attempt_count / cooldown_until
  pending_intent_id / pending_stage
  last_candidate_fingerprint
  last_model_score_id?
  draining
  bounded_rule_state
```

不存账户余额、Broker 订单副本、ExitPlan 状态或模型 artifact。

### 9.2 BoardDecisionSnapshot

一次周期冻结：

```text
BoardDecisionSnapshot
  snapshot_id / execution_id / cycle_sequence
  decision_time / trade_date
  config/model/rule bindings
  radar_frame_id / radar_frame_hash
  market_watermark / accepted_quote_watermark
  latest completed 1m bars by symbol
  latest accepted whole quote by symbol
  security/limit/price-tick facts
  user preference/arm versions
  account planning snapshot + public obligations
  snapshot_hash / quality
```

不要求所有股票同一毫秒报价，但必须记录每票 source time、age 和统一 watermark。超过 freshness、
来自未来或跨帧混合的数据不得进入候选比较。

### 9.3 BoardDecisionCycle

```text
BoardDecisionCycle
  execution_id / sequence
  cycle_id / snapshot_hash
  config/model/universe revisions
  status = PREPARED | COMMITTED | ABORTED
  evaluated/candidate/selected counts
  output_manifest_hash
  reason / timestamps
```

cycle id 由 execution、sequence 和 canonical snapshot identity 生成，不能包含随机 trace 或自身 ID。

material 周期必须原子提交：

- 每标的状态补丁；
- 候选及规则证据；
- frozen model score revision；
- 排名和 allocation decision；
- TradeIntent；
- cycle COMMITTED。

普通无变化行情只保留有界诊断，不强制逐 Tick 写库。

## 10. 纯决策内核

### 10.1 StrategyBase 适配器

`AshareLimitUpBoardAssistantStrategy` 逐步收敛为：

```text
StrategyInput[SNAPSHOT, execution_ref]
  -> 对每票调用 FirstBoard market policy reducer
  -> 输出候选提案 + BoardCandidateStatePatch
  -> 不读账户、不做最终排序、不算最终股数、不下单
```

`StrategyContext.run_id/mode` 和 `StrategyInput.run_id` 按公共契约改为
`execution_ref/environment`。普通 StrategyRun 由 adapter 映射，不在打板策略中保留 fallback。

### 10.2 Candidate proposal

```text
BoardOpportunity
  opportunity_id / execution_ref / cycle_id
  instrument_code
  radar_frame_id / quote identity
  rule_eligible / rule_reason
  signal_price / limit_up_price / distance_ticks
  model_score_id?
  preference/arm evidence
  candidate_fingerprint / expires_at
```

候选只表达市场机会，不表达最终股数、现金占用或已获授权。

### 10.3 硬门禁优先

以下任何一项失败，模型高分也不能恢复资格：

- 非沪深支持板块；
- ST、退市风险、停牌；
- 缺原生涨停价或最小价位；
- 一字板、已经封板或已经触及涨停；
- 不在入场窗口；
- 数据过期、未来数据或关键字段缺失；
- 已有同票 pending BUY、工作买单或配置禁止的新持仓；
- 账户只允许减仓、kill switch 或执行能力关闭。

## 11. BoardPortfolioCoordinator

### 11.1 职责

Coordinator 使用同一周期的候选、模型分数和账户规划快照：

- 稳定排序；
- 应用每日新增风险、单票、并发和行业集中度；
- 计算每票预算上限；
- 记录被淘汰和截断原因；
- 把 selected intent 标为等待人工确认。

它不能创建 Broker 订单、冻结真实现金或修改持仓。

### 11.2 BoardEntryEnvelope

打板使用专用、版本化且只读的 `BoardEntryEnvelope`：

```text
BoardEntryEnvelope
  account_snapshot_version
  total_asset / cash planning view
  max_daily_new_exposure
  max_single_position
  max_open_board_positions
  industry caps
  public pending BUY/SELL and active ExitPlan obligations
  computed_at / envelope_hash
```

它是一次规划输入，不是余额、Reservation 或仓位真源。最终资金和容量仍由
`AccountCapacityService` 在下单事务重新裁决。

不要复用 `TTradingEnvelope`：做 T 的 protected old-position floor 和库存置换语义与打板无关。

### 11.3 稳定排序

默认顺序由版本化 policy 明确：

1. 硬门禁通过；
2. 用户 PREFER（只在可交易候选中）；
3. ACTIVE 模型的校准质量/收益证据；`RULE_ONLY/SHADOW` 的真实排序都使用 RULE baseline；
4. 流动性、雷达阶段和距离；
5. instrument code 稳定 tie-break。

排名、预算、CAP 和淘汰原因写入不可变 `BoardAllocationDecision`。intent 只使用
`ALLOCATION_PENDING/SELECTED/REJECTED` 等业务状态；`CAP` 只属于 allocation action，不伪装成
订单状态。

## 12. 模型能力设计

### 12.1 模型定位

模型只回答：在当前点时首板候选和冻结执行假设下，这个候选的封板、次日触板/封板、成本调整收益
和尾损质量如何。

模型不能：

- 判断法规/交易合法性；
- 读取账户、持仓、偏好或授权作为特征；
- 输出目标股数、订单类型或最终价格；
- 越过 `FirstBoardEntryPolicy` 硬门禁；
- 因不可用而在 ACTIVE 中静默退回旧模型或规则排序。

### 12.2 三组状态严格分离

| 维度 | 状态 |
|---|---|
| training evidence | `BLOCKED / SHADOW_ELIGIBLE / ACTIVE_ELIGIBLE` |
| model registry | `CANDIDATE / SHADOW / ACTIVE / SUSPENDED / RETIRED` |
| execution scorer | `RULE_ONLY / SHADOW / ACTIVE` |

当前 `FirstBoardModelRelease.stage=SHADOW/PAPER/LIVE` 混合了证据、注册和交易环境，目标架构必须拆开。
`SHADOW` 分数只写审计、比较和漂移指标，不进入 executable rank、人工确认指纹或订单；其缺失、
陈旧、OOD 或推理失败不能改变 RULE baseline 结果。`ACTIVE` 分数会影响真实排名，因此任何不合法
状态都必须阻断受影响的新 BUY，禁止静默降级。

### 12.3 BoardFeatureSnapshot

模型输入冻结为：

- 日级点时事实：上市天数、近期涨停、价格位置、20 日收益、MA20 偏离、实现波动、流通盘；
- 已完成 1 分钟事实：涨速、量能/成交额进度、局部波动、板块梯队；
- 当前已接受 whole-quote：距离涨停、五档强弱、封板/炸板状态和 freshness；
- 市场/板块点时宽度，但不能包含未来当日收盘统计；
- 数据质量和字段 capability。

每份 snapshot 保存 `feature_as_of <= decision_at`、source watermarks、schema version 和 hash。实时 Tick
可以参与当次点时盘口特征，但必须先冻结为 snapshot；训练和回放使用相同 as-of 构建器，不能用日终
结果回填盘中输入。

禁止特征：账户现金、当前用户是否 PREFER、最终是否批准、实际下单数量、未来封板时长、当日收盘后
才能知道的成交统计，以及任何生成式 AI 文本结论。

### 12.4 BoardModelScore

```text
BoardModelScore
  score_id / model_version_id / feature_snapshot_id
  instrument_code / feature_as_of
  first_board_close_probability
  next_day_limit_touch_probability
  next_day_limit_seal_probability
  expected_net_return_pct
  cvar95_loss_pct
  calibration_bucket
  score_status = VALID | STALE | OOD | INVALID | ERROR
  inference_runtime / created_at
```

模型不直接输出不透明的仓位。Coordinator 使用版本化、可审计公式把上述量转成 rank evidence，并与
RULE baseline 比较。

### 12.5 标签与训练坐标

打板专用不可变数据集至少冻结：

- 全量满足发现阈值的 observation anchors，而不是只保存最终入选样本；
- signal/feature/outcome 时点；
- `first_board_close`；
- `next_day_limit_touch`；
- `next_day_limit_seal`；
- 在固定退出、费用、T+1 和成交情景下的 `net_return_pct`；
- tail loss/CVaR 评估样本；
- point-in-time Universe 和证券规则完整性。

同一模型比较必须使用相同 dataset hash、feature schema、label spec、split spec、cost/execution scenario、
random seed 和 segment policy。不同坐标的结果不能在 UI 中宣称优劣。

### 12.6 模型基准

第一阶段只比较：

1. `RULE_BASELINE`：当前可解释 radar/promotion 规则；
2. `LOGISTIC`：主板/成长板分段或带 segment 特征的可校准基准；
3. `LIGHTGBM`：只有在相同坐标下显著优于前两者且通过安全门禁才有 ACTIVE 资格。

当前固定系数 `FirstBoardPromotionEvaluator` 归入 RULE_BASELINE/SHADOW control。其版本号和输出可
继续用于历史对照，但不能登记为安全模型 artifact。

### 12.7 训练与发布复用

复用已经实现的公共 model-ops 原语：

- immutable dataset/spec/manifest/hash；
- `DEVELOPMENT` 与 `FINAL_EVALUATION` 隔离；
- FINAL test access 冻结、不可反复窥视；
- Prefect Worker 的阶段、进度、取消和业务幂等；
- 安全 artifact verifier、路径/符号链接/有限数值检查；
- CPU runtime self-test 和版本化数值容差；
- registry、人工登记/激活、审计事件和单一 ACTIVE；
- 同坐标模型比较和发布资格。

打板新增自己的强类型表/契约：

```text
board_model_datasets
board_model_dataset_versions
board_model_training_specs
board_model_training_runs
board_model_evaluations
board_model_versions
board_model_registry_events
board_feature_snapshots          # 仅 material/训练所需
board_model_scores               # material candidate 分数
```

不复用次日上涨或做 T 的 feature/label/model 表，也不创建 `task_type + feature_json` 泛化总表。

### 12.8 GPU 与在线推理

- GPU 只用于离线 LightGBM 训练；Engine 在线推理固定 CPU；
- Windows 使用经过资格验证的 OpenCL LightGBM，不引入 CUDA/WSL 生产依赖；
- backend 请求为 `CPU/AUTO/GPU_REQUIRED`，AUTO 不得静默把失败 GPU 宣称成功；
- 当前环境若为 `GPU_UNAVAILABLE_BUILD`，应安全使用 CPU 或阻断 GPU_REQUIRED；
- GPU 资格需满足内存上限、数值/排名/门禁结论容差和明确加速阈值；
- artifact 禁止 pickle/joblib 任意代码执行格式，GraphQL 不暴露服务器路径或 secrets。

### 12.9 Runtime binding 与失效

execution 只绑定已注册的 immutable model version/artifact hash。`ACTIVE` 模型不可加载、score stale、
OOD、artifact 被 suspend 或 runtime self-test 失败时：

- 停止新的 candidate 进入人工确认/下单；
- 已存在但未过期的人工确认立即失效；
- 已投递/结果未知 BUY 继续按原 owner 收敛；
- 已创建 ExitPlan 完全不依赖模型，继续执行。

不能自动寻找“最近一个可用旧版本”。切换 model binding 必须生成新 config version 和 successor
execution；旧 execution 只排空自身 BUY 义务。

`SHADOW` binding 的相同故障只产生稳定 shadow error 和指标，真实候选、排名、确认与订单继续使用
冻结 RULE baseline；不得把一次 shadow 故障误报成交易路径降级，因为模型从未进入该路径。

### 12.10 生成式 AI 边界

`LimitUpResearchJob/Artifact` 可以生成候选解释、新闻或风险摘要，但：

- 不进入 model feature；
- 不改变 `promotion_eligible`；
- 不改变 rank、预算、确认 TTL 或订单；
- 不作为 FINAL 模型证据；
- 失败不得阻断确定性交易安全链，UI 只显示“研究不可用”。

## 13. 人工确认与最终准入

### 13.1 冻结确认信封

人工确认绑定：

```text
execution_id / config_version / model_binding
cycle_id / opportunity_id / intent_id
instrument_code / candidate fingerprint
radar_frame / quote identity / effective_rank_evidence_id
active_model_score_id?
shadow_model_score_id?             # 仅审计，不进入授权指纹
max_budget / max_position / protected_limit
exit_plan_template_hash
account snapshot lower bound
expires_at / device session / user
```

`ARMED`、PREFER、模型高分或用户打开详情页都不等于确认。

### 13.2 EntryExecutionGate

确认消费后，进入账户最终锁前使用最新已接受事实按固定顺序重验：

1. execution/config/model binding 仍有效；
2. 候选未过期且仍在同一交易日/窗口；
3. 标的未停牌、ST、退市风险或已经封板；
4. 涨停价、price tick 和 protected limit 一致；
5. 最新报价 freshness、spread 和价格偏离满足 policy；
6. 同票没有新增持仓、pending BUY、工作买单或冲突 ExitPlan；
7. 账户允许增仓，kill switch、对账和 QMT ready 通过；
8. OrderSizer/Risk/Capacity 重新计算最终数量；
9. 仍不超过确认信封和 allocation 上限。

任一失败产生稳定 DELAY/REJECT 原因。确认不预留长期现金，也不保证最终成交。

### 13.3 排名顺序与原子容量

同周期多个已确认 intent 进入最终准入时，按冻结 rank 逐个在同一账户串行事务中处理。每次都重读
最新账户控制、public pending 和容量；前一票占用后，后一票可能少买或拒绝。

系统保证的是“准入顺序”，不是 Broker 成交顺序。outbox 保存 admission batch/rank 供审计。

## 14. 成交与退出

真实 BUY fill 原子完成：

- TradeIntent/Order/Execution 回报收敛；
- BucketLedger `swing` 归因；
- BoardTradeBatch/结果投影更新；
- 用冻结模板和真实成本创建确定性 ExitPlan；
- ExitPlan 保存 `source_execution_ref=BOARD_ASSISTANT_EXECUTION/execution_id`、candidate、模型、
  config 和 fill identity。

之后 SELL 完全由公共 `ExitPlanRuntime` 使用 owner `EXIT_PLAN/plan_id` 执行。打板 execution 不保存
PAPER/LIVE ExitPlanBook，也不因已成交持仓而必须一直运行。

禁用或升级助手时：

- 阻断新 cycle、candidate、approval 和未受理 intent；
- 尚未越过 Broker 边界的本地 BUY 可按权威规则取消；
- 已投递或结果未知 BUY 由原 execution DRAINING；
- 已激活 ExitPlan 独立继续；
- execution 自身 BUY 义务归零后可以 STOPPED，来源记录只归档不删除。

## 15. 持久化真源

| 事实 | 目标真源 | 说明 |
|---|---|---|
| 配置 head | `board_assistant_configs` | 单账户唯一，无 run id |
| 配置版本 | `board_assistant_config_versions` | append-only typed payload |
| execution | `board_assistant_executions` | PAPER/LIVE/BACKTEST owner |
| execution events | `board_assistant_execution_events` | 生命周期与恢复审计 |
| 每票状态 | `board_candidate_states` | execution + symbol，CAS |
| 决策周期 | `board_decision_cycles` | PREPARED/COMMITTED/ABORTED |
| 偏好/布防 | 现有 preference/arm 表 | 非 owner，单调版本 |
| Radar frame | Radar 持久快照/manifest | 训练、回放和 material 审计 |
| model dataset/run/version | board model 专用表 | 与交易 execution 分离 |
| material model score | `board_model_scores` | 绑定 feature/model/watermark |
| allocation | `board_allocation_decisions` | 不可变动作及淘汰原因 |
| BUY intent/order/report | 公共执行表 | owner ref |
| SELL | `auto_exit_plans` + 公共执行表 | owner EXIT_PLAN |
| replay | `board_assistant_replay_versions` | 不再依赖 StrategyRun |
| UI | `board_assistant_projections` | 可重建投影，不是真源 |

现有 `limit_up_board_assistant_configs` 可原子演进为 head；删除 `strategy_run_id`。现有 projection 保留为
查询优化，但任何恢复都不能依赖 projection payload。

## 16. 回放与回测

### 16.1 身份

每个回放创建：

```text
BoardAssistantExecution(environment=BACKTEST)
BoardAssistantReplayVersion
  replay_id / execution_id
  config/model/rule bindings
  dataset/frame/tick manifests
  scenario set version
  status/progress/result
```

不创建 StrategyRun，不接入实盘 approval、pending/outbox 或 QMT。

### 16.2 共享账户

回放必须在单一账户时间线上竞争现金、并发和仓位。不能将每只股票独立回测后相加。

固定 `STANDARD_V1` 的 THEORETICAL/FAST/BASE/STRESS 情景继续保留；情景参数是成交假设，不是模型
调参空间。

### 16.3 时间顺序

同一历史时点固定：

1. 既有订单消费当前 Tick；
2. ExitPlan 处理已有持仓；
3. Radar frame 和完整分钟特征变为可见；
4. StrategyBase.step 产生候选；
5. Coordinator 排名和预算；
6. 到期人工确认按情景延迟重验；
7. 新订单最早从下一条 Tick 撮合。

### 16.4 保守成交

- BUY 只消费委卖一至五中不高于限价的可见数量；
- SELL 只消费对应买档；
- 封板无卖盘不成交，跌停无买盘不卖；
- 不授予队列信用；
- 缺完整五档或证券状态时阻断，不使用乐观近似；
- 窗口末不强平，开放仓位按原因分类。

### 16.5 模型因果

每个历史 score 只能使用当时可用且训练截止早于测试日的 model version。若模拟模型迭代，必须以
walk-forward refit schedule 产生版本序列；不能用最终全样本模型回填整个历史。

## 17. 故障与恢复

| 故障 | 新 BUY | 已投递 BUY | ExitPlan | 恢复 |
|---|---|---|---|---|
| Radar stale/缺关键字段 | 停止 | 原 owner 收敛 | 继续 | 新鲜帧后恢复 |
| ACTIVE model 不可用 | 停止 | 原 owner 收敛 | 继续 | 修复同 binding 或建 successor |
| Engine 重启 | 停止至审计完成 | durable 恢复 | 优先恢复 | lease + DB 真源 |
| QMT 断线 | 停止 | RECONCILE_REQUIRED | 不生成新 SELL | 新鲜完整快照后裁决 |
| config/model 切换失败 | predecessor 不回切 | 原 owner 排空 | 继续 | 修复后新建 successor |
| candidate state CAS 冲突 | 当前 cycle abort | 不重复 intent | 无影响 | 重载并重放同 snapshot |
| report owner 冲突 | 全账户 fail-closed | 保留事实 | sticky error | 人工对账修复 |

恢复不能创建第二个 execution 接管结果未知订单，不能换 intent id 重发，也不能把旧 run 的 in-flight
命令改挂到新 owner。

## 18. 可观测性与 UI

### 18.1 审计链

```text
execution/config/model binding
 -> radar frame / feature snapshot
 -> rule eligibility
 -> model score
 -> rank/allocation
 -> candidate/intent
 -> manual confirmation/revalidation
 -> sizing/risk/capacity
 -> order/outbox

```

“没有买”必须归入明确类别：市场不合格、数据不健康、模型不可用、排名淘汰、额度不足、确认过期、
价格漂移、OrderSizer 为零、风险/容量拒绝或 Broker 未成交。

### 18.2 UI 状态分层

页面分开显示：

1. Radar 市场状态；
2. execution/environment/配置；
3. scorer mode 与模型证据；
4. 候选规则、排名和预算；
5. 人工确认；
6. 订单与真实回报；
7. 独立 ExitPlan。

删除 `strategyRunId` 作为助手主身份。旧实例只在迁移历史视图展示，不出现在新建、启停或确认 API。

模型概率、规则资格、人工偏好、已确认、已提交和已成交不能使用同一种颜色或状态名称。

### 18.3 指标

- Radar frame age、coverage、future-data reject；
- cycle lag、commit/abort、symbol CAS conflict；
- evaluated/eligible/scored/selected/confirmed/admitted/filled 漏斗；
- 模型 score freshness、OOD、推理延迟、校准和 rule/ML 排名漂移；
- allocation CAP、行业暴露、容量拒绝；
- approval TTL、价格漂移、订单 TTL、部分成交和无卖盘；
- outbox、ORDER/TRADE 延迟、ExitPlan 与 reconcile；
- training DEVELOPMENT/FINAL、backend、GPU 资格、artifact 和 registry 状态。

## 20. 迁移路线

### 阶段 0：冻结 StrategyRun 打板扩展

- 冻结账户级和旧单标的打板 StrategyRun schema/功能，除安全修复外不增加新能力；
- 清点 config、run、instrument state、候选、审批、pending、outbox、订单和 ExitPlan；
- 固定 Radar、首板规则、人工确认、ExitPlan、回放和模型研究基线；
- 建立 legacy owner 一致性与结果未知义务清单。

### 阶段 1：公共 owner 与 ExitPlan 前置能力

- 依照公共设计完成 protocol 1.2 和 `BOARD_ASSISTANT_EXECUTION` owner；
- 完成统一 ExitPlanRuntime，使旧来源计划可以保留 source run 但不依赖其热缓存；
- 所有 owner 缺失/冲突 fail-closed，不保留默认 StrategyRun。

### 阶段 2：配置与 execution

- 将现有 config 规范化为 config v1，删除 `strategy_run_id`；
- 新增 config versions、execution/events、candidate states 和 decision cycles；
- `mode` 迁移为 desired environment；`auto_exit_acknowledged` 不迁为授权；
- scorer 的旧 SHADOW/PAPER/LIVE 映射为独立环境、registry 和 scorer 状态，不能机械同名复制。

### 阶段 3：规则/Coordinator 影子

- 用相同 Radar frame 同时运行旧 StrategyRun 和新 snapshot runtime；
- 比较 Universe、规则原因、候选、排序、预算、确认重验和 ExitPlan 模板；
- 影子路径不写 intent、不消耗授权、不下单。

### 阶段 4：模型能力迁移

- 把当前固定系数 evaluator 标记为 RULE_BASELINE/历史 SHADOW；
- 物化打板专用 immutable dataset/spec/run/evaluation；
- 使用公共 Worker/GPU/artifact/registry 门禁训练 Logistic 与 LightGBM；
- 只有 FINAL+SUCCEEDED 且至少 SHADOW_ELIGIBLE 的结果可登记为 registry CANDIDATE；
- 人工晋升为 SHADOW 后只供 `scorer_mode=SHADOW` 的 execution，完成规定 shadow/回放/校准且证据为
  ACTIVE_ELIGIBLE 后，才允许再次人工晋升为唯一 ACTIVE 并由新 config 绑定。

### 阶段 5：新 owner 切换

1. 阻断 legacy run 新 candidate/approval/BUY；
2. 未越过 Broker 边界的旧候选和审批按稳定原因终结；
3. 已投递/结果未知 BUY 保留旧 STRATEGY_RUN owner 并 DRAIN；
4. 已有 ExitPlan 切到统一 ExitPlanRuntime，但保留原 source ref；
5. 创建新 LIVE BoardAssistantExecution，成为唯一新 BUY 来源；
6. 新 Coordinator 把 legacy 未决 BUY/持仓/ExitPlan 作为公共义务读取；
7. 旧 BUY 义务归零后停止并归档 run。

不得复制旧候选、重发旧 intent、转移在途命令或让两个 owner 同时对同票产生 BUY。

### 阶段 6：回放切换

- 回放创建 BACKTEST BoardAssistantExecution，不创建 StrategyRun；
- 保留四场景、共享账户、五档和窗口末语义；
- 历史 StrategyRun 回放只读保留，不作为新模型发布证据；
- 新 replay 表成为唯一新运行真源。

### 阶段 7：清理

- 删除 Engine 对 `StrategyRunRepository/runtime_manager.run_strategy` 的助手依赖；
- 删除 config `strategy_run_id`、StrategyRunState instrument state 和 metadata run fallback；
- 删除账户级助手专用 StrategyManager 恢复/停止分支；
- 普通单标的打板策略若仍作为真正用户策略存在，可继续使用 StrategyRun，但不作为助手入口；
- 新产品功能只使用账户级独立助手。

## 21. 测试要求

### 21.1 领域

- Radar frame 点时、future-data 和稳定 hash；
- Universe PREFER/IGNORE/ARMED/sticky 语义；
- 首板硬门禁、一字板、已封板、涨停价和 price tick；
- per-symbol pending、attempt、cooldown 和 fingerprint；
- Coordinator 稳定排序、tie-break、预算、并发和行业上限；
- model high score 不能恢复硬门禁。

### 21.2 模型

- dataset/spec/hash 不可变和 point-in-time Universe；
- observation anchor 覆盖、label outcome 时点和成本情景；
- walk-forward、分板块校准、Bootstrap、CVaR 和控制组；
- DEVELOPMENT/FINAL 隔离及 test access；
- artifact 路径、hash、有限数值、CPU self-test；
- GPU资格、无声 fallback 禁止、CPU/GPU 容差；
- SHADOW 缺失/陈旧/OOD/推理失败不改变 RULE baseline、确认或订单；ACTIVE 同类故障 fail-closed；
- registry 单一 ACTIVE、suspend、binding 失效和无旧版本 fallback。

### 21.3 应用与并发

- cycle 状态/证据/allocation/intent 原子提交；
- 同一 snapshot 重放不重复 intent；
- config/model successor 与 predecessor DRAINING；
- 同账户唯一 LIVE ENTRY producer；
- 人工确认 exact binding、TTL 和最新事实重验；
- rank 顺序下的最终容量串行；
- 禁用、重启和 CAS 冲突恢复。

### 21.4 执行与退出

- owner=`BOARD_ASSISTANT_EXECUTION` 的 BUY 全链；
- 订单 TTL、撤单和结果未知；
- partial fill、乱序回报和重复回报；
- 真实 fill 才创建 ExitPlan；
- source execution STOPPED 后 ExitPlan 继续；
- T+1 次日卖出、跌停无买盘和 sticky reconcile。

### 21.5 回放

- 同一 StrategyBase.step/Coordinator/scorer；
- 共享账户不能重复使用现金；
- 四情景确认延迟和盘口参与率；
- 新订单同 Tick 不成交；
- 无队列信用、窗口末不强平；
- BACKTEST 不写实盘 owner/outbox/QMT。

### 21.6 迁移

- legacy 在途 BUY 不改挂、不复制、不重发；
- config/state 规范化 hash 一致；
- 旧 ExitPlan 来源保留且由统一 runtime 唯一执行；
- 新 execution 无 strategy_run_id；
- 旧义务归零后无双写、fallback 和孤儿 run。

## 22. 上线验收

必须同时满足：

1. 启用、停用、配置和恢复打板助手不创建 StrategyRun。
2. 所有新 BUY 使用 `BOARD_ASSISTANT_EXECUTION/execution_id` owner。
3. config、execution、candidate state、cycle、model score 和 replay 都有独立真源。
4. Radar/规则/模型/偏好均不能读取账户或直接下单。
5. scorer mode、registry stage、training gate 和 execution environment 未混用。
6. ACTIVE 只绑定安全、不可变、通过 FINAL 门禁和 CPU self-test 的 artifact。
7. ACTIVE 模型不可用时停止受影响的新 BUY，不影响已投递命令和 ExitPlan；SHADOW 故障只记审计。
8. 人工确认后完整最新事实重验，最终数量由公共执行链决定。
9. 真实 BUY fill 才创建 owner=`EXIT_PLAN` 的独立退出计划。
10. predecessor 自身 BUY 义务归零后可终态，ExitPlan 仍完整恢复。
11. 回放不依赖 StrategyRun，且共享账户、五档和因果测试通过。
12. legacy run 全部排空，助手专用 StrategyRun 路径和 fallback 已删除。
13. SHADOW 分数从未进入可执行排名或授权指纹；ACTIVE 故障稳定阻断受影响的新 BUY。

## 23. 与做 T、买入/卖出计划的复用边界

| 可复用公共地基 | 打板助手必须独立拥有 |
|---|---|
| `ExecutionOwnerRef` / owner router | BoardAssistantConfig/Execution |
| `StrategyBase.step` 接口 | BoardDecisionSnapshot/CandidateState |
| TradeIntent、审批和设备挑战 | Radar/Universe/人工偏好语义 |
| OrderSizer、Risk、AccountCapacity | BoardPortfolioCoordinator/EntryEnvelope |
| pending/outbox/inbox、QMT 回报 | 首板规则、原因码、确认重验 |
| BucketLedger、Position、T+1 | BoardTradeBatch/结果投影 |
| 公共 ExitPlanRuntime | 首板 ExitPlan 模板 policy |
| immutable model-ops、Worker、GPU、artifact、registry | Board feature/label/score/model tables |
| replay manifest/任务生命周期原语 | 雷达帧、四成交情景和打板指标 |

禁止共享：

- `TAssistantExecution` 或 `EntryPlan` 作为打板 owner；
- `TTradingEnvelope` 或做 T 的 protected floor；
- 次日上涨/做 T 的 feature、label 或 model version；
- 任意 `AssistantRuntime[state_json]` 泛化容器。

## 24. 最终判断

打板助手的正确定位是一个“账户级、动态候选、强人工确认、模型辅助排序”的独立业务执行域，
而不是 StrategyRun 的特殊配置。

完成本设计后：

- Radar 负责发现；
- 规则负责资格；
- 模型负责可校准的质量证据；
- Coordinator 负责候选竞争和预算上限；
- 人工确认表达用户授权；
- 公共执行链负责最终合法数量和可靠订单；
- QMT 回报负责成交真相；
- ExitPlan 负责成交后的卖出；
- BoardAssistantExecution 只负责本次打板 BUY 的可恢复业务身份。

这些边界既去掉 `StrategyRun` 依赖，又让做 T、买入计划和打板助手能够真正复用安全基础设施，
而不是共享错误的生命周期和大而弱类型的运行状态。
