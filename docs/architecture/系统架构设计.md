**文档目标:** 定义面向 A 股个人量化的 QuantSaaS 全局架构：有哪些物理端、有哪些逻辑模块、状态如何在云端、本地 miniQMT 执行端与进化实验室之间流转，以及系统整体生命周期动作。本文不包含具体策略公式，只定义系统边界、状态真源、通信协议与不可推翻的技术决策。

## 0. A 股化设计摘要

本系统从原 7×24 加密货币现货架构调整为 **A 股单标的、双仓位 bucket、miniQMT 本地执行** 架构。

关键变化：

1. 交易对象从 `[交易所现货交易对]` 调整为 A 股 `instrument_code`，例如 `600000.SH` / `000001.SZ`。
2. 计价资金从 `USDT` 调整为 `CNY`，资产快照以人民币现金、冻结资金、股票总持仓、可卖量、今日买入量为核心。
3. 仓位语义从 `DeadStack / FloatStack / ColdSealedStack` 调整为 `core / swing / locked_core`。
4. 执行端从交易所 REST API 调整为用户本地 Windows 环境中的 miniQMT / QMT 客户端。
5. 系统必须显式处理 A 股交易规则：交易日历、交易时段、T+1、100 股整数倍、零股清仓、涨跌停、停牌、ST / 退市风险、手续费与印花税。
6. 实盘成交真源只来自 miniQMT 委托回报与成交回报；策略信号、下单成功、已报状态都不能被伪装成成交。

## 1. 架构哲学：时空正交、无记忆解算、成交真源隔离

**动作原则：** 所有业务推进必须封装为离散动作。每个动作读入当前状态快照，产出新的确定性意图或状态更新，不依赖上一动作遗留的内存变量。任何需要跨 tick 保存的内容都必须进入 `RuntimeState`、`PortfolioState`、订单状态或审计日志。

**窗口原则：** 每个模块只能读取属于自己的数据窗口和资金窗口。环境层读取大盘、行业、概念、市场宽度和成交量；策略层读取已加工后的 `StrategyInput`；风控层读取交易意图、组合状态、市场规则与订单状态；进化引擎读取历史数据和回测结果，但不能读取实盘账户凭证。

**A 股成交真源原则：** 实盘路径中，只有 miniQMT 返回的委托状态与成交回报可以改变真实成交状态。策略不得在发出信号后标记网格成交，SaaS 不得在下发指令后假定成交，Agent 不得把下单成功等同于成交。

**回测实盘同构原则：** 回测与实盘调用同一个 `Step()` 与同一套环境层、风控层、仓位调节层确定性规则。差异只存在于外圈 broker：实盘 broker 读取 miniQMT 回报，回测 broker 用历史行情保守模拟 A 股交易规则。

## 2. 三端物理部署形态

### 2.1 服务端管理与决策面（API + AI Runtime + Engine + Worker）

服务端由独立运行的 API、AI Runtime、Engine 和 Prefect Worker 组成。API 负责
HTTP/GraphQL、认证和 QMT Agent Hub；AI Runtime 负责产品内研究助手的模型
编排、只读工具、非交易写入审批和可恢复会话；Engine 独占策略推进、交易编排与
状态收敛；Worker 负责数据同步和批处理。四者共享 PostgreSQL 状态真源，但
生命周期互不从属。

职责：

1. 管理用户、订阅、策略模板、策略实例和冠军参数包。
2. 同步或读取 A 股历史与实时行情数据，包括个股、指数、行业、概念、市场宽度、交易日历、停牌、涨跌停与公司行为数据。
3. Engine 扫描 `RUNNING` 实例，并在最新已完成的日线或分钟聚合桶未处理时推进一次实例动作。
4. 构建 `MarketContextSnapshot`，执行确定性环境层。
5. 基于组合状态、市场规则和交易意图执行 SaaS 侧风控裁决。
6. 执行仓位调节层，调整动态天平的仓位边界、core/swing 拆分、现金缓冲和活跃度。
7. 调用策略 `Step()`，将策略输出的 `TradeIntent` 转换为经风控限额后的 `TradeCommand`。
8. Engine 先持久化 pending 订单与 outbox；API WebSocket Hub 再向用户本地 QMT Agent 下发 `TradeCommand`。
9. API 先将 QMT Agent 上报写入 inbox；Engine 消费后刷新 `PortfolioState`、订单状态、bucket 归因与审计日志。

SaaS 不做：

- 不调用 miniQMT。
- 不保存券商账户密码、交易密码、QMT 本地账号密钥或任何可直接控制交易账户的凭证。
- 不把交易指令下发视为成交。
- 在 `app_role: saas` 下不执行 GA 进化任务写接口和重型回测任务。

#### 2.1.1 产品 AI Runtime 边界

`quantx-ai-runtime` 使用 OpenAI Agents SDK，但模型编排不进入 API、Engine、
Worker 或 QMT Agent。API 只负责认证、GraphQL transport 和持久化 run 入队；
Runtime 通过 PostgreSQL 租约领取 run，把流式事件、消息、工具审计和待审批
`RunState` 写回数据库。Redis 仅用于低延迟唤醒，不能成为状态真源。

AI 工具可以读取用户获准的标的、账户投影、回测和研究结果；非交易任务创建
必须逐次人工批准并使用幂等键。`TRADING` 和 `ADMIN` 风险工具永久禁止，AI
Runtime 不连接 QMT Agent、不发交易命令、不推进订单状态，也不访问券商凭证。
连板分析和股票筛选应由现有领域/application/Worker 产出确定性结果，Agent 仅
负责解释结果或经批准创建任务。完整契约见
[AI Assistant 架构与集成指南](../engineering/ai-runtime/README.md)。

### 2.2 QMT Agent 执行端（用户本地 Windows 机器）

QMT Agent 是唯一允许访问 XTData/XTTrading 的本地执行进程，运行在能够
访问 miniQMT / QMT 的 Windows 环境中，只建立出站连接，不开放局域网监听
端口。

设备通过 UI 生成的一次性登记码完成绑定。设备密钥只保存在 Windows
Credential Manager；服务端仅保存哈希。miniQMT 路径、账户选择和券商配置
留在本地 QMT 环境，不进入服务端数据库、日志或网络消息。

职责：

1. 使用本地设备密钥从 API 换取短期 JWT。
2. 用 JWT 建立到 API `/ws/agent` 的 WebSocket 长连接。
3. 连接建立后发送本地账户资金、持仓、可卖量、冻结量、当日买入量和未完成订单快照。
4. 收到 `TradeCommand` 后立即返回 `command_ack`，随后在本地执行交易前保护检查。
5. 调用 miniQMT 执行下单、撤单、查询委托、查询成交、查询资产和查询持仓。
6. 订阅或轮询 miniQMT 委托与成交回报，构建 `DeltaReport` 上报 SaaS。
7. 定时发送心跳；断线后指数退避重连；重连后先做完整账户快照上报。

QMT Agent 可以包含 **本地执行保护规则**，例如交易时段校验、100 股整数倍校验、涨跌停价格校验、可卖量校验、可用资金校验。该保护规则不是策略，不生成新的买卖方向，只用于避免明显非法订单进入券商接口。

QMT Agent 不含：

- 策略 `Step()` 逻辑。
- GA 进化逻辑。
- 数据库连接。
- 自主交易决策。
- 改写策略运行状态的逻辑。

### 2.3 进化算力面（本地实验室，`app_role: lab`）

Lab 是完整 SaaS 系统的实验室部署，用于回测与 GA 进化。它可以连接同一个 Postgres，也可以连接只读复制库或本地研究库，但不得下发真实交易指令。

职责：

1. 拉取历史个股、指数、行业、概念、市场宽度、交易日历、停牌、涨跌停与公司行为数据。
2. 构造 A 股回测 broker，保守模拟 T+1、涨跌停、停牌、100 股整数倍、手续费、印花税、滑点、部分成交和不可成交。
3. 执行 GA 进化任务与候选参数回测。
4. 写入 `challenger` 基因包，等待人工审核后晋升为 `champion`。

Lab 不做：

- 不启动真实实例。
- 不连接 QMT Agent 下发交易指令。
- 不把回测成交写成实盘成交。

### 2.4 `app_role` 三态行为矩阵

| 角色 | 部署场景 | 开放能力 | 限制 |
|---|---|---|---|
| `saas` | 云端生产 | 用户、实例、行情快照、环境/风控/仓位调节、策略决策、WebSocket 指令下发、实盘状态收敛 | 禁止 GA/重型回测写接口；禁止保存券商凭证 |
| `lab` | 本地实验室 | GA 进化、回测、基因库管理、数据研究、候选参数产出 | 禁止实例启停；禁止交易指令下发；实例只读 |
| `dev` | 本机开发运行 | 所有模块可用；个人单账户默认保持完整 `full/live` 观察链路，经受控窗口、账户白名单、实盘总开关和精确确认后才授予自动执行 | 只有显式 `-Mode data-only` 才关闭实盘能力；QMT Agent 实盘子进程必须使用 `ENV=testing` 安全门，账户仍受快照、对账、备份、外部活动、灰度和 kill switch 门禁 |

## 3. 逻辑模块与责任边界

### 3.1 Strategy 策略模块（产品中心）

管理策略模板、参数结构、版本标识和 A 股适用范围。

当前主线策略：`ashare_dynamic_balance_dual_bucket`。

策略是单标的、双仓位、动态基准、Sigmoid 目标仓位策略。一个实例只绑定一个 `instrument_code`，不得在运行中自行切换标的。

`Step()` 是策略决策唯一入口。它读取 `StrategyInput`，输出 `StrategyOutput` / `TradeIntent`，但不直接计算 A 股合法下单数量，不读取真实可卖量，不调用 miniQMT，不写数据库，不假定成交。

策略内部只维护算法状态，例如趋势状态、动态基准、网格层级、core/swing 目标、pending 引用。真实资金、真实持仓、冻结状态、今日买入、可卖量与订单生命周期由执行与组合状态模块维护。

### 3.2 Market Data / Calendar 行情与日历模块

负责提供 A 股运行所需的数据真源。

数据范围：

- 个股日线、分钟线或 tick。
- 大盘指数、行业指数、概念指数。
- 市场宽度：上涨家数、下跌家数、涨停家数、跌停家数、炸板/连板数据（可用时）。
- 交易日历、交易时段、午休、节假日、临时停牌。
- 涨跌停价、price tick、ST / 退市风险标签。
- 公司行为：除权除息、分红、送转、配股等。

原则：

- 实盘信号使用时点可得数据。
- 回测不得使用未来复权因子、未来停牌信息或未来公司行为。
- 成交撮合使用未复权真实价格与真实涨跌停约束；指标可使用时点可得的复权序列，但必须保证无未来泄露。

### 3.3 Environment 环境层

环境层读取大盘、行业、概念、流动性、市场宽度和量价结构，输出 `MarketContextSnapshot`。

环境层只回答：当前外部环境是否支持冒险。

环境层不生成买卖方向，不修改仓位，不下单，不覆盖风控。缺少关键数据时只能降级为保守，不能给出更激进结论。

### 3.4 Risk 风控层

风控层是确定性规则模块，分为两类动作：

1. **上下文风控：** 根据环境、账户状态、风险阈值输出最大仓位、最大买入金额、是否禁止 swing 买入、是否进入防御 profile 等约束。
2. **订单意图风控：** 在策略输出 `TradeIntent` 后，校验交易时段、停牌、涨跌停、T+1、可卖量、100 股整数倍、现金、冻结、单票上限、低流动性、回撤和熔断。

风控层可以 `ALLOW`、`CAP`、`DELAY`、`REJECT` 或 `KILL_SWITCH`，但不得生成新的买卖方向，不得把拒单伪装成成交。

### 3.5 PositionAdjustment 仓位调节层

仓位调节层读取环境快照、上下文风控结果和当前策略状态，输出 `PositionAdjustmentProfile`。

它只调整动态天平的工作空间：

- `MinPct / MaxPct`
- `core_share / swing_share`
- `cash_buffer_pct`
- `balance_beta / inventory_gamma`
- `grid_step_multiplier`
- 是否允许 core/swing 买卖

仓位调节层不输出买卖，不计算合法手数，不修改真实账户状态。

### 3.6 Live / Instance 实例模块

实例的本质是：策略模板 + 单一 A 股标的 + 资金配额 + 风险配置 + bucket 归因账本 + 用户授权。

实例状态由该模块管理：`RUNNING` / `STOPPED` / `ERROR` / `KILL_SWITCHED` / `DELETED`。

实例 tick 只在最新已完成的数据桶未处理过时推进，避免实盘比回测多跑决策。A 股实例通常包含两类节奏：

- **日线收盘动作：** 更新趋势状态、动态基准、环境快照和 core 目标。
- **盘中动作：** 使用上一交易日确认基准与分钟/tick 数据触发 swing 网格。

### 3.7 Execution / Agent 执行模块

执行模块负责把 `TradeCommand` 转换为 miniQMT 可执行的委托，并把 miniQMT 回报转换为 SaaS 可收敛的状态。

执行链路：

```text
StrategyOutput / TradeIntent
  -> SaaS OrderSizer
  -> SaaS RiskChecker
  -> TradeCommand
  -> QMT Agent 本地保护检查
  -> miniQMT order accepted / rejected
  -> miniQMT order report
  -> miniQMT execution report
  -> DeltaReport
  -> SaaS RuntimeStateManager / PortfolioState
```

回测 broker 必须模拟同一条状态流，不能直接把策略信号当成成交。

### 3.8 Evolution & Backtest 进化与回测模块

通过 GA 对策略软参数进化，产出 `challenger` 参数包。人工审核后可 Promote 为 `champion`。

只在 `app_role: lab` 或 `dev` 下开放进化任务创建与执行。回测路径调用与实盘相同的 `Step()`、环境层、风控层、仓位调节层和订单状态流，只是 broker 从 miniQMT 替换为回测撮合器。

### 3.9 User / Auth 模块

处理用户注册、登录、JWT 签发、订阅计划和实例配额守门。此模块不涉及策略逻辑。

## 4. 全局状态总线

### 4.1 单一 Postgres + 单一 Redis

系统使用单一 Postgres 数据库作为状态真源。Redis 仅用于缓存、唤醒消费者
和实时订阅广播，不承担可靠投递或业务状态真源职责。

不得用 Redis Pub/Sub 或临时内存变量作为交易状态真源；Redis 不可用时
必须由数据库轮询恢复。

### 4.2 数据真源与所有权

| 数据 | 真源 | 说明 |
|---|---|---|
| 策略决策逻辑 | `Step()` 实现 | 回测与实盘共用；策略包纯函数 |
| 环境快照 | SaaS DB / 行情模块 | 由确定性环境层产出，可回测复现 |
| 风控裁决 | SaaS DB 审计 + 风控函数 | 每次意图必须留存结构化原因码 |
| 仓位调节 profile | SaaS DB 审计 + 仓位调节函数 | 不下单，只影响动态天平工作空间 |
| 冠军参数包 / 模板 | SaaS DB | 进化产出，供实例绑定 |
| 用户与订阅 | SaaS DB | 统一在 SaaS 管理 |
| 实例运行状态 | SaaS DB | `RUNNING` / `STOPPED` / `ERROR` 等 |
| 真实资金余额 | miniQMT 回报，经 Agent 上报后入 SaaS DB | 实盘真源是本地券商客户端 |
| 真实持仓、可卖量、冻结量、今日买入量 | miniQMT 回报，经 Agent 上报后入 SaaS DB | 策略不得自行维护真实状态 |
| bucket 算法归因 | SaaS DB | `locked_core / core / swing` 账本；必须与真实持仓快照可对账 |
| 委托与成交记录 | miniQMT 回报 + SaaS DB | pending / accepted / partial_filled / filled / rejected / canceled |
| 券商账户凭证 / 交易密码 / QMT 本地配置 | QMT Agent 本地环境 | 永不进入服务端 DB，永不通过网络上传 |
| GA 任务与基因记录 | SaaS DB | 单一数据库，无分库 |
| 历史 K 线、指数、行业、概念、市场宽度 | SaaS DB / Lab 数据库 | 回测与实盘决策的可复现数据源 |

### 4.3 本地券商凭证物理隔离铁律

任何券商账号、交易密码、资金密码、QMT 登录信息、柜台连接信息或其他可直接控制交易账户的凭证，只允许存在于用户本地环境或 miniQMT 自身配置中。

- 不进入 SaaS 服务。
- 不写入任何数据库表。
- 不通过 WebSocket、REST、日志或异常堆栈上传。
- 前端只显示“已配置 / 未配置 / Agent 在线 / Agent 离线”，不展示凭证内容。

发现 SaaS 侧代码保存或传输券商凭证时，必须立即停止开发并报告。

## 5. 云端下发与本地上报通信协议

云端与本地端严格遵循：**云端发意图与限额，本地执行保护，系统只信 miniQMT 上报。**

### 5.1 WebSocket 长连接模型

QMT Agent 主动连接 API `/ws/agent`。连接建立后第一条消息必须是携带短期
JWT 的 `auth`。API 验证通过后返回 `auth_result`，进入正常收发循环。

Agent 每 30 秒发送一次 `heartbeat`，SaaS 返回 `heartbeat_ack`。Agent 断线重连后，必须先发送完整账户快照，SaaS 据此对账与纠偏。

沪深实时行情不复用交易连接。活动行情 Agent 另建
`/ws/agent/market`，WebSocket 子协议固定为 `quantx.market.v1`；API 拒绝第二条
并发行情连接。miniQMT 端常驻唯一
`subscribe_whole_quote(codes)`，其中 `codes` 来自 QMT “沪深A股”与“沪深指数”
板块并在回调入口按同一集合再次过滤；随后按 `SNAPSHOT → DELTA` 和递增 sequence
发送 orjson 二进制批次。API 先原子更新 Redis 最新 tick Hash、stream 状态并
发布二进制批次，再返回 ACK。Engine `WholeQuoteHub` 订阅后补水并按本地标的
过滤扇出，页面或策略订阅变化不会触发 QMT 重订阅。

行情可靠性采用状态收敛而非 tick 重放。任意序号缺口、队列溢出、ACK 超时、
Redis 故障或连接中断都会进入 `SYNCING/STALE/OFFLINE`，暂停关键实时动作并由
最新全量快照恢复；不会用可能过时的中间 tick 触发交易。交易时段 10 秒无
新鲜批次判定 `STALE`，交易日历范围外不误报。

### 5.2 消息类型全表

| 消息类型 | 方向 | 触发时机 |
|---|---|---|
| `auth` | Agent → SaaS | 连接建立后立即发送，携带 JWT |
| `auth_result` | SaaS → Agent | 鉴权完成后返回 |
| `heartbeat` | Agent → SaaS | 每 30 秒 |
| `heartbeat_ack` | SaaS → Agent | 收到心跳后 |
| `command` | SaaS → Agent | 策略意图经 SaaS 风控和 sizing 后下发 |
| `command_ack` | Agent → SaaS | 收到 command 后立即确认，不等执行完成 |
| `order_report` | Agent → SaaS | miniQMT 委托状态变化，如已报、废单、撤单 |
| `execution_report` | Agent → SaaS | miniQMT 成交回报，包含部分成交与全部成交 |
| `delta_report` | Agent → SaaS | 交易执行后或重连时的完整资金持仓快照 |
| `cancel_command` | SaaS → Agent | SaaS 请求撤销未完成委托 |
| `report_ack` | SaaS → Agent | SaaS 成功处理上报后返回 |

### 5.3 TradeCommand 语义

每条 `TradeCommand` 携带以下字段：

| 字段 | 取值范围 | 说明 |
|---|---|---|
| `client_order_id` | 全局唯一字符串 | 格式：`inst{id}-{bucket}-{side}-{barTs}-{seq}` |
| `action` | `BUY` / `SELL` / `CANCEL` | 交易方向或撤单 |
| `instrument_code` | 如 `600000.SH` | A 股证券代码 |
| `order_type` | `LIMIT` / `MARKET_IF_SUPPORTED` | A 股普通股票 v1 默认限价单 |
| `limit_price` | decimal string | 下单价格，必须符合 price tick 与涨跌停 |
| `target_amount_cny` | decimal string | 买入时的目标金额，供审计与本地复核 |
| `target_volume` | integer | 实际委托股数，买入通常必须为 100 股整数倍 |
| `bucket` | `core` / `swing` / `locked_core` | 算法归因；`locked_core` 默认不能方向性卖出 |
| `phase` | 策略阶段 | 如 `BUILDING_CORE` / `BALANCED_RUN` / `DISTRIBUTION` / `DEFENSIVE` |
| `risk_decision_id` | string | 对应 SaaS 风控裁决记录 |
| `substitution_plan` | nullable JSON | T+1 库存置换计划，仅同标的内部有效 |
| `expires_at` | timestamp | 指令过期时间，过期不得执行 |
| `reason_tags` | string[] | 策略与风控原因标签，供审计 |

SaaS 下发 `TradeCommand` 前必须写入 pending 记录。Agent 收到后先 `command_ack`，再提交 miniQMT。只有 miniQMT 回报能把 pending 推进为 accepted / filled / rejected / canceled。

### 5.4 DeltaReport 语义

`DeltaReport` 包含：

- `client_order_id`：对应指令 ID；重连初始快照可为空。
- `broker_order_id`：miniQMT 委托编号。
- `order_state`：已报、部成、已成、废单、已撤、部撤等。
- `execution`：成交价格、成交量、成交金额、佣金、印花税、过户费、成交时间。
- `cash`：可用资金、冻结资金、总资产估值。
- `positions`：每只股票总持仓、可用持仓、今日买入、冻结数量、成本价、市值。
- `bucket_effects`：若本次成交涉及 core/swing/locked_core 归因或 T+1 库存置换，携带对应变化。
- `raw_payload_hash`：原始回报摘要哈希，供审计与重放。

### 5.5 状态收敛与天然自愈

SaaS 收到上报后：

1. 根据 `client_order_id` 查找 pending 订单。
2. 用 miniQMT 委托状态更新订单生命周期。
3. 只有在成交回报存在时才更新成交记录与 bucket 归因。
4. 用完整资金与持仓快照刷新 `PortfolioState`。
5. 对比 SaaS bucket 归因总量与 miniQMT 真实持仓总量；若差异超过阈值，进入 `RECONCILE_REQUIRED` 或 `ERROR`。
6. 写 `TradeRecord`、`OrderState` 与 `AuditLog`。

账户灰度状态必须区分“观察准备”和“自动执行”。在 `SHADOW`（准备阶段）且
自动执行未启用时，QMT 客户端产生的手工委托与成交属于合法外部账户事实：
服务端必须先持久化并标记为外部活动，再用完整快照收敛资金、持仓、委托和
成交；不能仅因缺少 QuantX `client_order_id` 就判定账实不一致。进入
`CANARY / LIVE` 后，未关联的外部活动仍会暂停自动执行，要求重新选择受控窗口
或人工处理 bucket 归因。无论处于哪个阶段，QuantX 已下发但在券商快照中缺失
的工作中委托都属于真实对账差异。

自愈机制：

- Agent 断线时，SaaS 跳过真实下发，不推进成交状态。
- Agent 重连后先发完整账户快照，SaaS 用真实持仓纠偏。
- SaaS 重启后从 DB 恢复 RUNNING 实例与 pending 订单，等待 Agent 重连后对账。
- 对账前不得把 pending 订单自动视为失败或成功，必须等待 miniQMT 或人工确认。

## 6. 系统级生命周期动作

### 6.1 系统初始化（System Init）

触发时机：SaaS 进程启动。

动作流转：

1. 读取 `config.yaml`，初始化 DB、Redis、JWT、行情数据源、交易日历和日志。
2. 执行 GORM AutoMigrate，以 Go struct 为唯一 schema 真源同步数据库结构。
3. 加载 A 股交易日历、交易时段、price tick、涨跌停规则和默认手续费配置。
4. 从 DB 读取 `RUNNING` 实例，注册到实例管理器。
5. 启动 WebSocket Hub，等待 Agent 连接。
6. 启动行情同步或行情读取模块。
7. 启动 cron 调度器，注册日线收盘任务与盘中分钟任务。

### 6.2 日线收盘动作

触发时机：交易日收盘后，最新日线 bar 完成且未处理。

动作流转：

1. 同步或读取当日个股、指数、行业、概念、宽度、成交额、涨跌停、停牌等数据。
2. 构建 `MarketContextSnapshot`。
3. 从 DB 读取 `PortfolioState`、bucket 归因、pending 订单、`RuntimeState`。
4. 执行上下文风控，得到最大仓位、现金缓冲、是否防御、是否熔断等约束。
5. 执行仓位调节层，得到 `PositionAdjustmentProfile`。
6. 构建 `StrategyInput`，包含收盘序列、时间戳、环境快照、组合状态、订单状态、仓位调节 profile 与风险约束。
7. 调用 `ashare_dynamic_balance_dual_bucket.Step()`。
8. 持久化新的 `RuntimeState`。
9. 对策略输出的 core 调仓意图执行 OrderSizer 和订单意图风控。
10. 对允许执行的意图写 pending 订单并通过 WebSocket 下发 Agent。
11. 更新实例的 `LastProcessedDailyBarTime`。

### 6.3 盘中分钟 / tick 动作

触发时机：连续竞价时段内，最新 1m/tick 数据桶完成且未处理。v1 推荐仅支持连续竞价：09:30–11:30、13:00–15:00。

动作流转：

1. 读取上一交易日确认的动态基准与日线目标仓位。
2. 读取当前分钟/tick 价格、盘口可用信息、涨跌停价和停牌状态。
3. 读取 `PortfolioState`、可卖量、今日买入、冻结量、bucket 归因与 pending 订单。
4. 构建盘中 `StrategyInput`。
5. 调用同一个 `Step()`，只允许产生盘中 swing 相关意图或强风控相关意图。
6. 对意图执行 sizing 与风控：交易时段、涨跌停、T+1、可卖量、库存置换、现金、单日新增仓位、pending 去重。
7. 写 pending 并下发 Agent。
8. 更新 `LastProcessedIntradayBarTime`。

### 6.4 Agent 断线重连

触发时机：Agent 检测 WebSocket 断开。

动作流转：

1. 初始等待 1 秒后重连，每次失败翻倍，最大 5 分钟。
2. 重新登录获取 JWT。
3. 建立 WebSocket 并发送 `auth`。
4. 鉴权通过后立即发送完整 `delta_report`：资金、持仓、可卖量、今日买入、冻结量、未完成委托。
5. SaaS 对账 pending 订单和 bucket 归因。
6. 对账完成前，实例可进入 `RECONCILING`，禁止新增买入，保留人工处理入口。
7. 对账成功后恢复正常 tick。

若账户仍处于 `SHADOW`，这里的“恢复”只表示观察与账户事实链路回到准备就绪，
不授予自动下单权限；从自动对账暂停中恢复时也只能回到 `SHADOW`，不得静默
恢复到 `CANARY / LIVE`。

### 6.5 熔断与人工恢复

触发时机：风控层输出 `KILL_SWITCH`。

触发条件示例：

- 实例净值回撤超过最大允许回撤。
- 单标的连续跌停且无法卖出。
- 持仓快照与 bucket 账本严重不一致。
- miniQMT 长时间无委托/成交回报。
- 标的 ST、退市风险、长期停牌或重大异常。

熔断后：

1. 实例状态进入 `KILL_SWITCHED`。
2. 禁止新增买入。
3. 未完成委托可撤单或等待回报。
4. 已有卖出意图进入人工确认或只允许降风险模式。
5. 必须写审计日志。
6. 恢复只能由人工触发，恢复前必须完成账户与 bucket 对账。

### 6.6 优雅停机与状态快照

触发时机：SaaS 接收到 `SIGTERM` / `SIGINT`。

动作流转：

1. 停止接受新的 Agent 连接和新的 cron tick。
2. 等待进行中的 tick 完成，设置超时保护。
3. 持久化活跃实例的 `RuntimeState` 和 pending 状态。
4. 给 Agent 发送关闭帧。
5. 关闭 DB、Redis、行情源连接。
6. 停机期间不得丢弃 miniQMT 已上报但未处理的消息；消息处理失败必须记录可重放日志。

## 7. 不可推翻的技术决策

以下为整个系统硬约束，违反时必须停止开发并报告。

**1. 复利前置条件**

任何策略机制必须能说明收益如何回到资金规模中滚动：目标仓位基于总权益计算，盈利增加可用权益与后续订单规模，亏损降低风险暴露和后续下单空间。不能论证复利性质的策略不进入开发。

**2. 策略同构原则**

回测与实盘必须调用同一个 `Step()` 实现。`Step()` 内部禁止 `if isBacktest` 之类分支。策略逻辑只在 SaaS / Lab 侧执行，Agent 不包含策略代码。

**3. 策略纯函数原则**

策略包内部禁止定时器、网络请求、数据库读写、文件 I/O、系统时间读取。策略只依赖传入的 `StrategyInput`，只输出 `StrategyOutput`。

**4. A 股交易规则优先**

所有实盘与回测必须遵守：交易日历、交易时段、T+1、100 股整数倍、零股清仓、price tick、涨跌停、停牌、ST / 退市风险、手续费、印花税、过户费。任何策略意图不能突破这些规则。

**5. miniQMT 成交真源**

下单成功、已报、信号触发都不是成交。真实成交状态只能由 miniQMT 成交回报驱动。回测 broker 也必须模拟订单生命周期，不能把信号直接当成交。

**6. 本地券商凭证物理隔离**

券商账号、交易密码、QMT 配置和任何可控制交易账户的凭证只允许存在本地，不进入 SaaS，不写数据库，不通过网络上传。

**7. 标的范围与动态 universe 原则**

默认固定标的策略一个实例只绑定一个 `instrument_code`，策略不得在运行中自行换股。账户级策略只有在显式声明 `INSTRUMENT_SCOPE=MULTI` 与 `INSTRUMENT_UNIVERSE_MODE=ACCOUNT_HOLDINGS` 时，才允许由外部持仓快照协调器动态维护 `instruments`。动态策略代码仍不得查询账户、数据库或 miniQMT；标的增删必须通过运行时串行事件队列进入同一个 `StrategyBase.step(RECONCILE)`，并保留审计记录。

**8. bucket 三态语义**

仓位归因使用 `locked_core / core / swing`：

- `locked_core`：用户封存仓，默认不方向性卖出；仅在显式允许时可作为同标的 T+1 库存置换来源，且总量不下降。
- `core`：长期核心仓，建仓期受保护，后续可慢进慢出。
- `swing`：短期波动仓，围绕动态基准交易。

bucket 是算法归因，真实持仓与可卖量以 miniQMT 为准。

**9. T+1 库存置换必须可回滚**

使用 core 或 locked_core 可卖老仓完成 swing 当日买入后的卖出，只是同标的库存置换，不得突破 T+1。卖单拒单、撤单、部分成交都必须按成交数量回滚或部分确认。

**10. 无量纲计算**

策略和环境层中的跨标的比较必须使用收益率、比率、分位、ATR 倍数、相对强弱等无量纲指标。不得用绝对价格跨股票比较。

**11. 数据无未来泄露**

回测中不得使用未来复权因子、未来公司行为、未来停牌、未来涨跌停或未来订单结果。所有输入必须是评估时点已知数据。

**12. GORM AutoMigrate 为唯一 schema 真源**

数据库结构以 Go struct 为真源，通过 GORM AutoMigrate 管理。不写 SQL migration 文件，不维护版本化 migration 脚本。

**13. 单一数据库，无分库**

服务端使用单一 Postgres。Redis 只做缓存、唤醒和广播，不作为交易意图或
订单状态真源。

**14. 用户界面零内部术语**

面向用户的字符串不得裸露内部字段名、状态机名或公式片段。`core / swing / locked_core` 应展示为“核心仓 / 活跃仓 / 封存仓”。希腊字母若必须出现，应加文字释义。
