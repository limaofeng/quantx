### 已确认的故障机制

生产新请求 `f5c4e931-2363-4bab-ba3b-1d80a140458c`（本轮 batch2）在第一个工作单元
复现了此前的候选机制：

1. 23:59:19.449 原生下载完成，完成回调至返回约 0.199 ms。
2. 23:59:19.646 首次读取 `300319.SZ/1m` 返回 **241 行、0 有效行、241 占位行**。
   判定直接复用上传过滤谓词：OHLC 全部不可用，volume/amount 均为零。
3. 23:59:19.647 触发第一次缓存重读，等待 0.1 秒；23:59:19.755 读取完成。
4. 最终该标的投影为 **241 行、241 有效行、0 过滤行**，时间范围为
   `1788831000000` 至 `1788850800000`；没有再次下载。

这确认了本轮现场存在“原生完成后先读到非空占位帧，稍后缓存可读”的时序。
旧代码只用 `len(frame) == 0` 判断重试，241 行占位帧直接绕过重试，随后被全部过滤，
因此上报无数据；不是 Influx 写入或并发回读丢失。旧失败批次没有保存原始帧，仍不能
逐行重建其现场，也不声称已查明 XTData 内部缓存更新实现。

第三批新请求 `27a1b715-80ad-4643-a69b-214830c04480` 又在第二个工作单元复现：
2026-09-09 00:00:45.529，`300342.SZ/1m` 为 241 原始行、0 有效行；同样仅一次
0.1 秒缓存重读，最终恢复 241 有效行。该机制不限于原标的 `300319.SZ`。
