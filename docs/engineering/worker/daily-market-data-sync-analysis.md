# daily-market-data-sync 长区间分析

分析日期：2026-09-08。下列 4/5/6 章节保留实施前的代码与内存评估，作为优化对照。
当前实现与部署要求以 [Worker README](README.md) 为准。

## 已实施结果

- 15 秒独立心跳覆盖规划、等待、入库、回读和运行内重试；Agent 心跳提供工作单元与
  上传字节进度，普通请求日志归属 Flow。日志查询改读最新页。
- Tick 同日最多 10 个标的，周期独立分区。11 标的、21 交易日的纯 Tick 从 231 请求
  降至 42 请求；全市场 7,552 标的对应 15,876 请求，仍受实际字节硬限约束。
- 单一历史进程按工作单元轮转请求，保留未结束的生成器状态；共享磁盘预算与 QoS
  不变。暂停/恢复轮转不重复下载，子进程丢失时未完成准备请求仍须重新准备。
- Flow 不累计完整审计，分区证据持久化、分页查询；已结束 Flow 仍可显示后台请求
  后续入库结果，覆盖未经校验时不伪装合格。
- 两次重试在同一个 Running 状态内部执行，保留部署并发门禁，避免旧部署租约在
  AwaitingRetry 后继续续约。失败样例和前后端日志缓存均有界。

以下数字是实施前测量/推算，不代表优化后的实盘耗时；本次不启动真实 QMT 下载。

## 4. 请求数量与实际执行开销

外层持久化请求与内层 XTData 工作单元是两层分区：

- Worker 同时等待最多两个请求；Agent 的历史准备锁仍串行使用同一个历史进程。
  双路主要重叠上传、摄取、回读等阶段，不是两路并行调用历史 XTData。
- `runtime._ensure_historical_worker_sync` 复用存活的历史子进程，不是每批启动进程。
- `historical_worker.historical_work_units` 把非 Tick 按 20 个标的分组，Tick 按 10 个；
  内层日期窗口分别是 Tick 1 天、1m 1 天、1d 31 天。内层按自然日拆分，分钟线
  跨月请求仍包含周末、节假日工作单元。
- 当前外层 Tick 固定为单标的单交易日，所以无法利用内层 10 标的批量能力。
  混选的日线和分钟线跟随 Tick 分区，也退化为逐标的逐日调用。

取 7,552 个存续标的、31 个自然日、21 个交易日，按代码规划计算：

| 周期 | 外层每批标的 | 持久化请求数 | 内层工作单元数 |
| --- | ---: | ---: | ---: |
| 1d | 300 | 26 | 378 |
| 1m | 53 | 143 | 13,268 |
| 1m + 1d | 53 | 143 | 13,696 |
| tick | 1 | 158,592 | 158,592 |
| tick + 1m + 1d | 1 | 158,592 | 475,776 |

方法：使用当前 `_market_data_request_batch_size` 的预算公式，并提取实际
`historical_work_units`、`_chunks`、`_date_windows` 函数计算工作单元数。
未调用 SDK；表中未扣除上市边界，未估计网络、压缩、数据库速度。
即便 1m 的外层只有 143 批，内层仍有一万余个工作单元，不能用批次数直接估算耗时。

此外，每个请求都有持久消息、spool、上传清单、摄取租约和完成审计；逐标的回读还
会按最多 2,000 个上传键拆批、串行查询。摄取会三次读取压缩分片，分别用于写前
校验、写入、上传键回读校验。这些正确性保障有成本，不应简单删除来提速。
Agent 上传已有双路和 8 MiB/s 限速；单请求上限 500,000 条、解压 512 MiB、压缩
256 MiB，本地总 spool 预算 512 MiB。提高 Worker 并发不改变历史准备串行事实，
却会加重排队、内存和 spool 压力。

建议：

1. 先取得下载、编码、上传、摄取、回读的阶段耗时与字节数，再决定优化对象。
2. Tick 优先尝试“同一天多个标的”，例如 10 个：上述请求数变为
   `ceil(7552/10) × 21 = 15,876`，约减少 90%。同时保留逐标的逐日审计和失败定位。
   这只是候选值，必须结合实测单 Tick 字节数验证上述硬上限，不能只看记录数。
3. 混选时评估把非 Tick 周期独立分区，避免日线/分钟线被迫跟随最细的 Tick 分区。
4. 内层 1m 可评估多日小窗口或显式交易日列表，但须保持可抢占性及实时行情健康门。
   当前隔离工作路径等待 IPC 消息的上限是 30 秒，不能把备用线程路径的 15 分钟
   超时当作它的实际限制；扩大工作单元前应测量最慢单位耗时。

验收应同时记录完成时间、请求/工作单元数、上传字节、重试数和实时行情健康，不能
通过增加第二个历史调用者或绕过 QoS 获得表面吞吐。

## 5. 内存不是只有行情 DataFrame

行情写入批次已限制 2,000 行或 8 MiB，分片也有记录与字节上限；但整个 Flow 并非
固定内存。`_persist_validated_records` 为股票、周期、自然日的笛卡尔积创建
`daily_counts`，之后转换成逐日字典列表；完整 `day_coverage` 写入 PostgreSQL JSON。
`_request_market_data_batches.results` 保留所有批次审计，最终又通过 `transfer.batches`
返回。后者主要是引用，不应误算成一次深拷贝，但仍延长全部结果的存活时间。

隔离测量使用当前函数中的初始化循环和 `day_coverage` 列表表达式，通过 AST 提取后
执行。样本 300 个标的、单周期、31/365 个自然日；用 `tracemalloc` 分别测量列表
创建后保留分配、`json.loads` 新增分配和紧凑 JSON 大小，再按 7,552/300 外推。
样本零记录覆盖行用于测量审计结构，不模拟实际成交数据。

| 范围 | 全市场覆盖明细条数 | 列表创建保留量（外推） | JSON 解码分配（外推） | 紧凑 JSON（外推） |
| --- | ---: | ---: | ---: | ---: |
| 31 天、一个周期 | 234,112 | 60.1 MiB | 75.1 MiB | 20.1 MiB |
| 365 天、一个周期 | 2,756,480 | 645.2 MiB | 883.9 MiB | 236.6 MiB |

以上不是进程 RSS 或峰值，未计入其他摘要、DataFrame、分区表、校验集合、临时
JSON 字符串、Prefect 状态等。多个周期接近线性增加；本次新增的逐日存在性校验也
会产生仅存活于当前批次的非空覆盖键集合。批次更小只能降低这类瞬时分配，不能
解决 `results` 累积全部审计的总量。Tick 的 158,592 个独立请求还各有摘要与对象开销。

建议首先让 Flow 返回紧凑统计、请求 ID 和缺口摘要，完成一个批次的验证后释放详细
审计；详细证据继续保存在持久化真源。即便结果持久化功能未启用，这也能降低运行中
的内存，而不是仅减少最终序列化量。
随后再评估 `day_coverage` 的存储表达，不能直接删除零行：当前回放/快照审计使用
逐日空数据作为证据，必须同步修改读取者和验证语义。分区规划可改为惰性迭代，避免
一次性构造所有 Tick 分区。此次未改这几项数据结构及返回契约。

## 6. 日志存在可见性与阶段信息两类缺口

本地 `.venv` 使用实际 Prefect `setup_logging()` 的隔离检查结果：

```text
extra_loggers = []
root_level = WARNING
quantx_worker.prefector.flows.durable_agent_flows INFO enabled = False
request logger own_handlers = []
```

`_request_and_wait` 使用普通模块 logger，因此当前默认配置下“Created market-data
request” INFO 会被过滤，也没有 Flow 的 API 日志 handler。主 Flow 使用
`get_run_logger()`，所以参数和批次完成日志可进入 Flow 日志。部署进程若另有环境
覆盖，应单独验证，不能仅凭源码中写了 `logger.info` 就断定用户可见。

目前等待循环没有状态变化/定期进度；Agent 已收到 `started.total_units` 和
`checkpoint.completed_units`，但只校验数值、执行 QoS、回复 continue，没有把进度
向用户输出。下载接口有 callback 参数，调用方未传。主 Flow 完成日志缺少分区日期
和耗时，而且并发时 `batch=N/total` 表示分区编号，不是已经完成 N 个分区。
本次仅为失败后继续处理补充了失败分区的日期、代码、周期和错误，尚未改成功日志。

建议按层输出：

- Flow 开始：目标范围、实际分区数、周期、并发、跳过的非存续范围。
- 请求开始与状态变化：Flow ID、request ID、分区范围及 queued/preparing/uploading/
  ingesting/verifying 阶段；Worker 编排日志使用 run logger，通用基础设施由调用者
  传入日志或显式配置 handler，避免全局打开所有库的 INFO。
- 每 15–30 秒限频汇总：已完成/失败/跳过/总分区、当前请求、阶段耗时和累计字节。
  必须用完成计数，不能用乱序返回的批次编号充当进度。
- 完成时汇总耗时、保存/验证记录数、缺口数量；逐小分区成功日志降到 DEBUG 或采样。

已有 checkpoint 是首先可以使用的进度来源。缺少分母或吞吐尚未稳定时不输出伪精确
ETA。错误继续逐分区保存证据，但不反复打印同一堆栈；不能输出账户、设备密钥等
与历史数据同步无关的信息。当前日志文件不足以重建一个完整月度运行，所以本报告
没有给出实际阶段占比。

## 建议实施顺序

先补阶段观测和限频汇总，再缩减 Flow 内存中保留的审计详情，最后用阶段测量选择
Tick 合批与内层窗口优化。数据库证据、逐日缺口判定、取消恢复和实时 QoS 都应保留。
