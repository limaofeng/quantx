## 1. 问题与结论

当前用户在 `confirmManualOrder` 成功后会看到“下单请求已进入队列”，
但 Web 没有可恢复的排队列表。页面只用交易卡片内存中的
`trackedClientOrderId` 查询单笔 `manualOrderAttempt`；刷新、切换标的、关闭页面或
重新登录后，该 ID 丢失，状态也随之不可见。现有 `OrderRecords` 只查询
`todayOrders/historyOrders`，它们是券商委托投影，不包含尚未生成
`broker_order_id` 的本地排队请求。

修复结论：

1. 以已持久化的 `PendingTradeOrder + TradeCommandOutbox` 作为“下单请求”真源，
   不新建第二套状态表。
2. 在现有“委托”工作区增加独立的“下单请求”页签，与“当日券商委托”、
   “历史券商委托”明确分层。
3. 排队、已投递、Agent 已回执都不得显示为“券商已受理”或“下单成功”。
   只有出现 `broker_order_id` 后，才能显示“券商委托已生成”。
4. 刷新、切换标的和重新登录后都从服务端列表恢复，不依赖 React 内存或
   `localStorage` 保存交易事实。

## 2. 不可破坏的边界

- miniQMT 委托与成交回报仍是实盘真源。
- `command_ack` 只表示 Agent 已收到命令或已完成本地前置检查，不是券商接受、
  部分成交或已成交。
- 已进入 `DELIVERED` 但券商结果不确定时，不得乐观终结。存在任何券商副作用
  证据或矛盾关联时必须显示 `RECONCILE_REQUIRED`。
- “下单请求”记录不得伪造 `Order`，不得混入券商委托的撤单、成交量和委托
  状态逻辑。
- 本项目是个人单账户系统；不为此修复新增多账户、多租户、通用工作流或
  未确认的通知抽象。

## 3. 目标事实流

```text
confirmManualOrder
  -> PendingTradeOrder + TradeCommandOutbox        下单请求真源
  -> manualOrderAttempts                           Web 可恢复列表
  -> QMT Agent 投递 / ACK                     仍然只是请求阶段
  -> broker_order_id + 券商委托回报        委托事实开始
  -> todayOrders / historyOrders                   券商委托列表
  -> 券商成交回报                               持仓、资金与成交真源
```

两个列表可以通过 `client_order_id / broker_order_id` 关联，但不合并为同一种记录。

## 4. GraphQL 契约修复

### 4.1 用复数查询取代单笔内存追踪

在同一次原子变更中，用最近请求列表取代现有只能按 ID 查询的
`manualOrderAttempt`：

```graphql
manualOrderAttempts(
  accountId: String
  limit: Int = 50
): ManualOrderAttemptFeed!

type ManualOrderAttemptFeed {
  items: [ManualOrderAttempt!]!
  totalCount: Int!
  activeCount: Int!
  requiresAttentionCount: Int!
  truncated: Boolean!
  asOf: DateTime!
}
```

- `limit` 最小为 1，最大为 100，系统默认 50；首版不增加游标分页。
- 查询只返回当前认证用户、解析后的唯一账户、`bucket = manual` 的记录。
- 排序优先级为：需对账 > 未终结 > 已终结；同组内按 `created_at DESC`。
  这保证最近终态不会把需处理的请求挤出可见区。
- `totalCount` 和 `truncated` 让前端在超出 100 条时明确显示“仅显示前 N 条”，
  不得把截断列表显示为全量。
- 前后端在同一轮删除单笔 `manualOrderAttempt` 与其查询文档，不保留双协议、
  fallback 或旧字段兼容分支。

### 4.2 由服务端投影统一阶段

`ManualOrderAttempt` 保留底层 `status` 与 `deliveryStatus` 供审计，同时新增
类型化 `phase`，前端不再自行猜测两个原始状态的组合。

```text
ManualOrderAttemptPhase =
    QUEUED
  | DELIVERED
  | AGENT_ACKNOWLEDGED
  | BROKER_ORDER_CREATED
  | REJECTED_BEFORE_BROKER
  | EXPIRED_BEFORE_BROKER
  | CANCELLED_BEFORE_BROKER
  | RECONCILE_REQUIRED
```

投影优先级必须保守且唯一：

| 真源证据                            | `phase`                   | Web 文案                   | 是否继续轮询 |
| ----------------------------------- | ------------------------- | -------------------------- | ------------ |
| 任一状态为 `RECONCILE_REQUIRED`     | `RECONCILE_REQUIRED`      | 结果待核对，禁止重复下单   | 是，低频     |
| 存在 `broker_order_id` 且无对账异常 | `BROKER_ORDER_CREATED`    | 券商委托已生成             | 否           |
| 无券商证据且明确下单前拒绝          | `REJECTED_BEFORE_BROKER`  | 未生成券商委托：已拒绝     | 否           |
| 无券商证据且明确过期                | `EXPIRED_BEFORE_BROKER`   | 未生成券商委托：已过期     | 否           |
| 无券商证据且明确取消                | `CANCELLED_BEFORE_BROKER` | 未生成券商委托：已取消     | 否           |
| `ACKNOWLEDGED`                      | `AGENT_ACKNOWLEDGED`      | Agent 已回执，等待券商委托 | 是           |
| `DELIVERED`                         | `DELIVERED`               | 已投递，等待 Agent 回执    | 是           |
| `QUEUED/PENDING`                    | `QUEUED`                  | 已排队，等待下发           | 是           |
| 无法安全解释的组合                  | `RECONCILE_REQUIRED`      | 状态不确定，需核对券商端   | 是，低频     |

明确禁止在出现 `broker_order_id` 或其他券商副作用证据时投影为
`REJECTED_BEFORE_BROKER / EXPIRED_BEFORE_BROKER / CANCELLED_BEFORE_BROKER`。

### 4.3 列表字段

列表项至少包含：

- 身份与关联：`accountId`、`clientOrderId`、`brokerOrderId`。
- 委托内容：`instrumentCode`、`side`、`orderType`、`limitPrice`、`volume`、
  `executionMode`。价格保留精确 Decimal/字符串口径，不以浮点数返回。
- 阶段：`phase`、`active`、`requiresAttention`、`status`、`deliveryStatus`、
  `statusReason`、`message`。
- 时间线：`createdAt`、`deliveredAt`、`acknowledgedAt`、`expiresAt`、`updatedAt`。

上述字段全部来自现有 `PendingTradeOrder` 和 `TradeCommandOutbox`，不需要新增数据表。
列表解析器不应顺带查询或拼接券商成交；已有 `brokerOrderId` 时只提供到券商委托
列表的确定性关联。

### 4.4 认证、授权与性能

- GraphQL 操作继续要求 `orders:read`，并通过 `_resolve_account_id` 限制到当前唯一账户。
- SQL 必须同时过滤 `user_id`、`account_id` 和 `bucket = manual`，不得只依赖
  `client_order_id` 的全局唯一性。
- 首版直接使用当前表与索引，不做推测性数据库迁移。只有实际查询计划证明需要时，
  才另行增加精确的组合索引。
- 列表 resolver 只读，不推进任何订单、outbox 或对账状态。

## 5. Web 信息架构与交互

### 5.1 唯一入口

持仓页保留现有一级“委托”工作区，将其内部页签改为：

1. **下单请求**：展示本地排队、Agent 投递、Agent ACK、下单前终结和对账异常。
2. **当日券商委托**：继续使用 `todayOrders`。
3. **历史券商委托**：继续使用 `historyOrders`。

必须在页签文案中出现“下单请求”和“券商委托”，不用只有开发者能理解的
`Pending/Outbox/ACK` 作为主标签。

交易卡片中现有“下单状态（尚非券商委托）”可以保留为当次交互摘要，
但必须改为从列表查询中按 `clientOrderId` 选中的派生视图，不再是唯一入口。
确认入队后提供明确的“查看下单请求”操作，打开“委托 > 下单请求”并
高亮本次 `clientOrderId`。高亮丢失不影响刷新后恢复整个列表。

### 5.2 列表展示

列表使用工作台紧凑表格，至少展示：

- 入队时间、证券代码、买入/卖出、LIVE/PAPER、价格类型与价格、数量。
- 当前阶段、最近更新时间、服务端原因。
- 存在 `brokerOrderId` 时显示“查看券商委托”；关联不确定时不提供猜测性跳转。
- 右键菜单允许复制 `clientOrderId`、`brokerOrderId` 和证券代码。

“下单请求”行不提供“撤单”或“再次下单”。只有真实券商委托行沿用现有撤单能力。
`RECONCILE_REQUIRED` 必须展示“禁止重复下单，请先核对券商端”，不提供快捷重试。

### 5.3 加载、空状态与错误

- 初次进入、账户切换或会话恢复后执行 `network-only` 查询。
- 无记录时显示“暂无下单请求”，不显示“暂无委托”。
- GraphQL 错误必须显示可读原因和“重新加载”，不得用空列表掩盖查询失败。
- 已有成功数据后的刷新错误可保留上次结果，但必须显示“状态可能已过期”和上次
  更新时间。
- 登录失效进入现有鉴权刷新/登录流程；登录成功回到持仓页后重取服务端列表。

### 5.4 轮询与刷新

首版使用自适应轮询，不为本项修复新建 GraphQL 订阅：

- 当列表中存在 `QUEUED / DELIVERED / AGENT_ACKNOWLEDGED` 时，且页面可见，每 2 秒
  `network-only` 刷新。
- 存在 `RECONCILE_REQUIRED` 但无其他活动请求时，页面可见期间每 10 秒刷新。
- 全部为已终结请求时停止定时轮询；窗口恢复焦点、页签重新显示或用户点击
  “刷新”时重取。
- `confirmManualOrder` 成功后立即重取列表，不等待下一个轮询周期。
- 页面不可见时暂停轮询，避免持续请求。

### 5.5 视觉与无障碍

- 状态颜色使用系统语义：排队/等待为 `state.warning`，投递/ACK 使用现有
  中性文字与蓝色信息强调，券商委托已生成为 `state.success`，拒绝/过期/对账异常为
  `state.danger`；不新造未登记的颜色 Token。
- 买入/卖出方向仍使用 A 股红买绿卖，但不以方向颜色表达请求成功与否。
- 颜色不是唯一信息载体；每个阶段都显示明确文字、最近更新时间和原因。
- 表格遵循标准/紧凑密度 Token，不新建任意像素字号或大圆角卡片。
- 动态状态变化通过 `aria-live="polite"` 宣告；错误和对账异常使用可读文案，
  不只显示红色边框。

## 8. 测试与验收

### 8.1 API 和契约测试

- 仅返回当前用户、当前账户和 `manual` bucket。
- 账户越权、缺少 `orders:read`、非法 `limit` 都被拒绝。
- 需对账、活动、已终结的排序和计数正确；超过 limit 时 `truncated = true`。
- `QUEUED -> DELIVERED -> ACKNOWLEDGED -> BROKER_ORDER_CREATED` 投影正确。
- 只有能证明“从未形成券商副作用”时才投影下单前拒绝/过期/取消。
- `RECONCILE_REQUIRED` 优先于 `broker_order_id` 的普通已生成状态。
- resolver 调用不修改 Pending、Outbox、Order 或任何账户事实。
- 公开 GraphQL schema、operation policy、Web 查询和生成类型一致。

### 8.2 Web 测试

- 组件首次挂载直接从服务端显示既有排队请求，不需要当前会话的
  `trackedClientOrderId`。
- 刷新、切换证券、会话恢复后仍能显示同一请求。
- 确认入队后立即显示新行，“查看下单请求”能打开对应页签并高亮。
- 排队、已投递和 Agent ACK 不显示“券商已受理/已成功”。
- 下单前拒绝、过期、取消和需对账均显示明确原因；需对账无重试按钮。
- 券商 ID 出现后才显示券商委托关联，不把请求行合并成 `DisplayOrder`。
- 错误与空状态可区分；截断、数据陈旧和更新时间可见。
- 定时轮询在页面不可见或全部终结时停止，活动状态变化后使用正确频率。
- 买卖方向颜色与系统阶段颜色不混用，键盘焦点和 `aria-live` 可用。

| Agent 返回 ACK                 | 显示“Agent 已回执，等待券商委托”，不显示“已受理” |
| 出现 `broker_order_id`         | 显示“券商委托已生成”，可跳转到券商委托列表       |
| 下单前明确拒绝或过期           | 显示“未生成券商委托”和服务端原因                 |
| 结果无法确定                   | 突出显示“需核对券商端，禁止重复下单”             |
| 列表查询失败                   | 显示错误与重试，不显示伪空列表                   |

## 9. 完成定义

同时满足以下条件才可将修复标记为完成：

- 当前账户的手工下单请求有一个可发现、可刷新恢复的 Web 列表。
- 下单请求和券商委托在 API 类型、前端组件、文案和操作上都没有混同。
- 页面刷新、切换标的和会话恢复不会丢失排队状态。
- `command_ack` 不会在任何 UI 显示为券商接受或成交。
- 需对账状态是显式的，且不提供自动重试下单。
- 查询是当前用户/账户下的有界只读查询，不新增状态表或推测性迁移。
- GraphQL codegen、TypeScript、lint、Vitest、生产构建和相关 API 测试全部通过。
- 工程文档已更新，本计划已记录实际实施与验收结果。

## 10. 非目标

- 不新增真实下单、撤单、重试或对账 mutation。
- 不修改 QMT Agent 下单、ACK 和回报契约。
- 不把 Pending/Outbox 记录复制到 `orders` 表。
- 不为首版新增 GraphQL subscription、消息推送或桌面通知。
- 不扩展到策略自动单、买入计划、退出计划或做 T 的状态 UI。
- 不为此修复增加多账户、多租户或未确认的历史归档功能。
