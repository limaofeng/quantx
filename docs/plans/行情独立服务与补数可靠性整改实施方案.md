# 行情独立服务与补数可靠性整改实施方案

日期：2026-09-09。状态：重构进行中，P1 恢复基础和 P2 独立 API/Worker 基础已实现；尚未执行生产操作。

依据：[目标设计](行情独立服务与补数可靠性整改方案.md)。本文将目标设计落实到代码范围、
依赖顺序、迁移步骤和验收证据；不代表目标设计中的生产事实已重新核验。
实施基线采用三进程、18085 历史 API、唯一 Agent 专用历史会话和 4:1 公平调度。
这些仍是设计参数，不是已上线配置。生产变更以完成验证后的精确迁移清单为准。

## 1. 实施顺序与完成定义

按 P0 → P1 → P2 → P3 → P4 → P5 → P6 单代理推进。每个阶段先完成最小整链，
再补受影响边界；代码可以分批提交，生产只进行一次协调切换，不并行运行新旧推进者。

| 阶段 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- |
| P0 定位与基线 | 调用/写入清单、只读复现工具、原任务证据索引 | 明确失败查询或记录无法取得原证据的阻塞项 |
| P1 回读与恢复基础 | 有界扫描、错误分类、持久化 checkpoint/预算 | 合成故障和断点测试通过；真实扫描问题有明确结论 |
| P2 最小服务整链 | Data API、Data Worker、租约、一个分区的证明 | 提交→合成上传→写入→回读→证明；旧 owner 失效测试通过 |
| P3 原子迁移所有入口 | Gateway、Agent 历史会话、调用方和 writer | 无旧推进者、无直接历史写入旁路，进程隔离验证通过 |
| P4 开发交付与可观测性 | 导出/导入、状态 UI、公平性、Monitor | 隔离环境跨端整链及断点恢复通过 |
| P5 迁移演练与上线清单 | 数据迁移、备份校验、精确部署和恢复步骤 | 隔离恢复演练通过，上线清单包含实际任务和验证证据 |
| P6 原任务及完整周期验收 | 两个上传、50 个需求、盘后及重启验收 | 原设计验收矩阵逐项有结论；成功和缺数分别统计 |

P0 无法访问生产原始 manifest 时，可以用合成样本推进本地 P1—P4；这不满足真实扫描
修复退出门，也不能据此进入生产切换。开发实现通过和生产恢复通过分别记录。

## 3. P0—P1：先建立可靠摄取基础

### 3.1 原失败复现

新增只读诊断入口，输入明确 request ID 和已有 manifest，复用真实预期键生成与校验器。
不得创建请求、写 Influx、修改状态或触发 QMT。输出任务 ID、manifest hash、分组序号、
页游标、时间范围、键数、SQL 指纹、脱敏参数范围和结构化错误码。

原设计列出的两个 request ID 为复现对象；实际 manifest 路径由运行端只读查询确定，
不在代码中猜测。Mac 不连接生产数据服务：生产复现在 Windows 运行端执行，
本地使用经授权提供的证据或合成样本。诊断不能输出凭据、服务端路径到业务响应。

入口已实现为 `ops/diagnose_market_data_readback.py`。它按 ID 在只读、可重复读事务中
加载原请求及分片目录，再验证现存文件；没有 claim、resume、写入或发布证明的操作。
必须在 `quantx` Conda 环境运行并显式选择环境；Mac 拒绝 production，本地 development
仍校验本机独立数据服务。原任务 Windows 只读复现命令（尚未执行）：

```powershell
New-Item -ItemType Directory -Force .runtime/diagnostics | Out-Null
conda run -n quantx python ops/diagnose_market_data_readback.py --environment production --request-id 98632b5b-24b0-4bcc-a178-792f2694dcab --output .runtime/diagnostics/readback-98632b5b.jsonl
conda run -n quantx python ops/diagnose_market_data_readback.py --environment production --request-id d1cc696b-3e7d-446b-9842-39755db92268 --output .runtime/diagnostics/readback-d1cc696b.jsonl
```

输出文件以独占创建防止覆盖证据；每条记录写后刷新。退出码 0 表示当前上传键回读通过，
1 表示扫描或证据失败，2 表示配置/输出准备失败。JSONL 保留 manifest 指纹、校验阶段、
分组索引/指纹、分组键数、扫描索引、分页索引、时间条件、参数指纹和异常类型。
例如原始 `ValueError` 会在 `query_error` / `reader_error` 中保留异常类型，而不泄露
原始 provider 消息。查询仅一路、无阶段重试，沿用既有拆分和每组 60 秒预算；分组键数
是拆分前预期数，扫描索引区分子范围。诊断成功不会修改任务状态，也不证明全天覆盖。

### 3.2 有界查询

1. 在保留各标的精确范围的基础上增加整个分组的顶层半开时间条件。
2. 页大小 2000、分组最多 20 标的/10000 键；继续验证完整预期键集合。
3. 仅扫描容量错误触发时间二分，必要时拆标的；不同子范围严格无遗漏、不重复计数。
4. 单组共享最多 32 节点、深度 8、60 秒的初始预算。预算覆盖分页、拆分和底层调用，
   配置实际查询超时和取消；不能只在阻塞调用返回后检查时间。
5. 单键/最小区间失败或预算耗尽，持久化 `DEPENDENCY_QUERY_CAPACITY_BLOCKED`。
   对连接异常使用阶段重试预算，不嵌套启动另一套重试。

对相同完整预期键比较修改前后结果，测试重复毫秒 Tick、分页边界、额外已有行、缺键、
空 reader、取消和拆分终止。正常查询不得因新增拆分逻辑无条件增加扫描。

### 3.3 分阶段恢复

将“内容校验→写入确认→回读→证明”拆成可恢复阶段。checkpoint 至少绑定
`request_id / attempt / manifest_hash / phase / block_index`；确定批次顺序，
只有目标写入确认后才提交该块 checkpoint。未知写入结果幂等重写当前块。

重试状态落 PG，初始最多 4 次执行（首次加 3 次重试），退避 5/30/120 秒，
总窗口 5 分钟；进程重启不刷新额度。确定性认证/配置/容量阻塞立即停止同操作。
读回失败保留已确认写入，恢复只重做失败回读。显式恢复保留原 ID 和历史 attempt，
新 attempt 必须记录操作者/原因；自动探针不得偷偷重新建立预算。

## 4. P2：数据模型、接口和最小完整链

### 4.1 服务结构

新增 `apps/market-data/pyproject.toml` 和 `src/quantx_market_data/`：

| 入口/目录 | 职责 |
| --- | --- |
| `gateway.py` | 独立实时进程，搬迁现有 Gateway 后去除业务 API 导入 |
| `api.py` | 18085 HTTP/历史 WS；仅认证、校验、持久化和有界查询 |
| `worker.py` | PG 租约循环、阶段推进、恢复及保留期清理 |
| `bootstrap.py` | 环境校验和依赖装配，不导入业务 API 或 QMT SDK |

DTO 放 contracts；用例和端口放 `packages/application` 的行情模块；仓储、文件与
Influx/HTTP 适配器放 infrastructure。新应用不复制 infrastructure 实现。
同步根 `pyproject.toml` 的 workspace、依赖和 pytest 路径；依赖操作显式使用
quantx Conda Python，不创建 `.venv`。

### 4.2 持久化设计

保留 `market_data_request` 作为采集任务和原 ID。迁移应先检查已有列、约束及索引，
复用已有能力；以下是逻辑对象，不要求每个对象另建一张表。

| 对象 | 必须保存的事实/约束 |
| --- | --- |
| 数据需求 | 分区口径、来源、调用方关联；相同分区并发提交依靠数据库唯一约束去重 |
| 采集任务 | status/phase、reason、stage attempt、next retry、progress、manifest hash |
| 采集许可 | owner epoch、有效期、任务和有界单元 ID；投递/确认幂等 |
| checkpoint | 阶段、稳定块号、写入/验证结果；与 manifest 和 attempt 绑定 |
| 分区证明 | 键摘要、行数、覆盖、源身份、数据/校验版本及完成时间 |
| 交付任务 | 原 export ID、固定版本、分片 hash、远程关联、下载进度和本地证明 |
| 依赖阻塞 | 能力与失败范围、探针时间、恢复条件；区分单任务与共享依赖 |
| 实时归档 | 有界批次、幂等键、接收事实、写入进度；超限产生明确缺口 |

采集 status 使用 `QUEUED/RUNNING/BLOCKED/COMPLETED/FAILED/CANCELLED`，phase
记录具体阶段；交付状态单独定义，不把 `LOCAL_VERIFIED` 塞进采集状态。
完成证明和采集终态在同一 PG 事务发布。需求提升优先级不产生重复采集。
取消单个需求先解除关联，只有不存在其他有效需求时才取消共享采集。

### 4.3 API 与租约

接口包括需求提交、状态、取消/恢复、历史分页读取、参考数据、导出分片、Agent 历史
会话和上传、内部实时归档接收。提交返回持久化 ID；GET 不推进任务，不创建 attempt。
状态区分 `last_progress_at` 与 `observed_at`，给出阻塞原因、恢复条件和关联任务。

需求接收已改为 `POST /market-data/internal/v1/demands`，返回持久化 demand_id；
`GET /market-data/internal/v1/demands/{id}` 只读返回分区、来源、采集/交付关联和状态。
原内部 POST `/requests` 尚无已迁移调用方，已原子替换；采集请求的 GET 和显式恢复
仍使用 `/requests/{id}`。`0066` 保存需求目录，分区与本环境来源生成稳定 ID，
未关联需求最多 5000 个，同 ID 再次提交不重开、不消耗名额。生产 Worker 持租约选择
在线来源并在同一事务建立采集任务及关联；离线保留原 ID，30 秒后再探测，不创建摄取
attempt，不更新实际进展时间。开发来源由服务配置固定为 REMOTE，只在同事务建立
本地交付目录，禁止调用 QMT。LINKED 表示已关联任务，不表示数据已验证完成。
当前独立 Worker 尚未接管远程下载/导入执行；该整链仍属于 P4 剩余工作。

已实现内部本地读取 `GET /market-data/internal/v1/history`：必填 instrument、period
（tick/1m/1d）、trading_date，page_size 默认 1000、最大 2000，after 是上一页返回的
UTC 存储时间。查询范围是上海交易日的半开区间，Tick 时间包含可逆 ordinal；校验每条
记录的范围、身份及严格递增。返回 records（Tick 深度采用存储层平铺字段）、next_after、
exhausted；非空短页仍继续探测，只有空页 exhausted=true。分页结束不等于覆盖证明，
此接口不触发补数、不转发远端。单次查询及连接池等待共享 10 秒预算，Arrow 结果累计
最多 4 MiB；API 仅一个在途查询，繁忙返回 429，查询失败返回脱敏 503，不内部重试。
API 与持久化回读各分配一路；统一启动必须固定一个 Data API 进程，服务总预算仍须在
P3 移除旧调用旁路、P4 接入参考查询/导出后验证，不能据此宣称现有系统已全局限流。

权限至少区分本环境业务调用、开发受限行情调用、Agent 历史会话；开发凭证不得取消
其他调用方任务或访问 Agent/归档/交易端点。历史 token 校验身份、用途、有效期与撤销。
端点路径和 DTO 在 P2 定稿并同批更新调用方，不保留旧新两套调度语义。

Worker 使用 PG 租约和单调 fencing epoch；所有状态推进、许可签发及 checkpoint 更新
均带有效 owner 条件。Influx 无 PG 事务 fence，因此失租后停止派发新写入、取消在途工作，
未知结果按确定块幂等恢复；旧 owner 不得提交 checkpoint/发布证明。Agent 校验许可有效期、
epoch 及已执行单元 journal，拒绝旧许可。实时 Redis 通知只用于唤醒。

先用一个合成分区贯通上传到证明，再测失租、重复上传、写入后退出和重启恢复。
最小整链通过前不展开全部 UI 和历史调用方迁移。

## 5. P3：入口、QMT 与写入所有权切换

限权认证基础已实现：`POST /auth/agent/history-token` 接收既有 `deviceId` 和
`deviceSecret`，返回独立的短期 `accessToken` / `accessTokenExpiresAt` / `deviceId`。
历史 token 的权限必须精确为 `agent:history`；交易及实时 Agent 校验拒绝带此权限的
token，历史校验拒绝无该权限或附带额外权限的 token。签发与验证读取当前设备撤销状态，
验证还检查绑定设备、用户和到期时间。共享实现位于 `quantx_infrastructure.auth`，
不依赖业务 API；设备登记和签发端点仍由身份权威提供。
Agent 上传已调用历史令牌端点，分片/完成/失败端点与 Caddy 路由已迁至 Data API；
专用历史 WS 和 Worker 采集许可运行链路仍待迁移。新版上传拒绝旧交易令牌，部署须协调更新 Agent。

原生单元拆分已提取至 `quantx_contracts.collection_permit.plan_historical_work_units`，
Agent 在调用共享拆分前仍校验整个原请求的记录预算；拆分不重置请求额度。保留现有
Tick 每批 10 标的/一天、分钟线每批 20 标的/一天、日线每批 20 标的/31 天及平衡分组规则。
`CollectionUnit` 用计划版本、原请求 ID、零基单元序号和原生参数摘要形成稳定身份，
传输路径与许可元数据不参与参数摘要。未来 4:1 调度必须基于这些单元，不能按整个长请求计数。

`CollectionPermit` 绑定设备、单元、owner epoch、许可 ID 和最多 30 秒的启动有效期。
Agent journal 已提供持久化接收校验：写锁内检查 epoch 水位、许可 ID 和单元身份，
拒绝过期/未生效、错设备、旧 epoch 和冲突重放；重启保留水位。许可回执仅表示接受过
启动授权，不能作为原生完成或上传完成证明。重复许可仍须加入或恢复已有 request/spool。
Data Worker 许可仓储基础已实现，迁移 `0067` 持久化许可和生产连续完成单元计数。
签发核对原请求、设备、共享拆分身份及已完成的前序单元；许可启动截止不超过当前租约。
数据库部分唯一索引限定全局只有一个 ISSUED/STARTED 单元，同一请求序号不能重复执行。
未启动许可过期后保留原记录，以新许可 ID 重发同一单元；STARTED 不因截止时间或租约
过期释放。新 owner 可以收敛该单元的真实完成确认，旧 owner 不能推进；重复确认不计数。
生产完成计数上限为 4，开发完成才清零，签发、重发和启动不会改变计数。
共享拆分最多生成 2048 个单元，防止异常持久化请求展开无界目录；Agent 原请求预算仍先校验。

仓储已增加 `0068` 原请求计划目录：保存计划版本、完整原生参数摘要、总单元数和下一单元序号；
登记后拒绝改变计划。FINISH、下一单元推进与公平计数同事务提交，重复确认不重复推进。
`issue_next` 在同一租约和调度行锁内选择、签发：生产连续完成不足 4 时优先生产，
