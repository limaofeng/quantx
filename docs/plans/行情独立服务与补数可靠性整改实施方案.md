# 行情独立服务与补数可靠性整改实施方案

日期：2026-09-10。状态：实施计划已按当前代码更新，P1 恢复基础和 P2 独立 API/Worker 基础已实现；历史执行整链尚未完成，尚未执行生产操作。

依据：[目标设计](行情独立服务与补数可靠性整改方案.md)。本文将目标设计落实到代码范围、
依赖顺序、迁移步骤和验收证据；不代表目标设计中的生产事实已重新核验。
实施基线采用三进程、18085 历史 API、唯一 Agent 专用历史会话和 4:1 公平调度。
这些仍是设计参数，不是已上线配置。生产变更以完成验证后的精确迁移清单为准。

## 1. 实施顺序与完成定义

按 P0 → P1 → P2 → P3 → P4 → P5 → P6 单代理推进。每个阶段先完成最小整链，
再补受影响边界；代码可以分批提交，生产只进行一次协调切换，不并行运行新旧推进者。

| 阶段 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- |
| P0 定位与基线 | 调用/写入清单、只读复现工具、原任务证据索引 | 明确失败查询或记录无法取得原证据的阻塞项 |
| P1 回读与恢复基础 | 有界扫描、错误分类、持久化 checkpoint/预算 | 合成故障和断点测试通过；真实扫描问题有明确结论 |
| P2 最小服务整链 | Data API、Data Worker、租约、一个分区的证明 | 提交→合成上传→写入→回读→证明；旧 owner 失效测试通过 |
| P3 原子迁移所有入口 | Gateway、Agent 历史会话、调用方和 writer | 无旧推进者、无直接历史写入旁路，进程隔离验证通过 |
| P4 开发交付与可观测性 | 导出/导入、状态 UI、公平性、Monitor | 隔离环境跨端整链及断点恢复通过 |
| P5 迁移演练与上线清单 | 数据迁移、备份校验、精确部署和恢复步骤 | 隔离恢复演练通过，上线清单包含实际任务和验证证据 |
| P6 原任务及完整周期验收 | 两个上传、50 个需求、盘后及重启验收 | 原设计验收矩阵逐项有结论；成功和缺数分别统计 |

P0 无法访问生产原始 manifest 时，可以用合成样本推进本地 P1—P4；这不满足真实扫描
修复退出门，也不能据此进入生产切换。开发实现通过和生产恢复通过分别记录。

### 1.1 后续实现批次与执行入口

本次准备沿用已有实现和第 9 节检查点，不重新搭建服务。工作区中尚未提交的协议、
Agent 和相关测试改动需先核对归属、完成审核与验证，不能计入已验收基线。
下面按依赖顺序执行，每批交付可独立审核的完整改动；全部批次完成才满足目标整改。

| 批次 | 实现范围与接口交付 | 本批退出条件 |
| --- | --- | --- |
| 1 实时会话独立 | Gateway 认证、连接身份和撤销检查；Agent 实时握手解除对交易控制注册的等待 | 交易控制会话缺失或更替不使独立实时身份失效；撤销设备和旧实时连接仍被拒绝；协议及部署校验一致 |
| 2 历史最小整链 | contracts 定义专用历史会话及许可 START/FINISH 回执；Data API 投递、Worker 推进、Agent 执行一个有界单元 | 单需求从许可到不可变单元文件、上传、写入、回读及证明完整通过；各确认边界断开后能按原 ID 恢复 |
| 3 历史执行接管 | bars、Tick、参考字段、因子、日历、证券资料、财务和板块全部接入同一许可与原生锁；删除旧控制面派发 | 全部采集入口有明确归属；无旁路、双 owner 或另一套重试；4:1 计数及交易 QoS 在真实调度循环生效 |
| 4 业务读取与归档 | API、Engine、通用 Worker、研究/训练改用本机 Data API；实时 K 线改为有界归档提交 | 静态引用盘点和受影响测试共同证明历史读写无旁路；归档满载不阻塞策略事件循环，缺口可追踪 |
| 5 开发交付 | Worker 接管固定版本导出、远程关联、分片下载、校验、导入及本地证明 | 断网、重启、损坏分片和源版本变化保留原关联与预算；成功项达到 LOCAL_VERIFIED |
| 6 状态与运行验收 | GraphQL/Web、Monitor、两端启动器及能力探针 | 展示实际阶段、进展、原因和恢复条件；实际 Caddy 契约检查通过；隔离环境故障矩阵有证据 |
| 7 迁移和原任务验收 | 隔离迁移演练、最终生产清单、两个上传及 50 个需求对账 | 原 ID、文件和证据保真；逐项通过或明确缺数/阻塞；完整盘后及重启恢复周期验收完成 |

批次 2 是继续扩展历史入口前的首要整链门。先确定消息字段、幂等键、确认落盘顺序和
断线恢复规则，再同时接入 Worker、Data API 和 Agent，不先扩展所有调用方。
Agent 必须先保留可校验的单元文件和 journal 完成事实，才能发送 FINISH；
FINISH 表示原生单元完成，不能等同于上传完成、持久化证明或需求完成。
已 START 的单元不能因租约超时直接重采；以 journal、文件和服务端记录对账，
无法证明结果时明确阻塞。旧 spool reset 和清理逻辑不得删除尚被引用的单元文件。

各批次证据统一记录提交号、环境、测试命令及结果、尚未执行的退出条件。
本地替身测试只证明对应逻辑；Windows 原生执行、实际服务停止后的连续性和生产数据
完整性必须分别验收。普通实现测试不授权 E2E、真实交易、生产迁移或服务重启。

开始本地实现无需等待生产材料，但进入原任务验收前必须取得两个原始 manifest、
50 个需求到源请求及交付 ID 的完整映射、原 ValueError 的精确用户任务 ID。
这些材料缺失时记录待验收，不把合成样本结果填入原任务对账表。

### 1.2 当前起点与首批实现任务

2026-09-10 本地核对：批次 1 的实时认证解耦已有实现；批次 2 的历史 WS 服务端、
Worker 调度、START/FINISH 回执和 Agent 单元执行器已有基础。`runtime.py` 仍从交易
控制连接启动 `_market_request_loop`，历史 QoS 仍首先依赖控制连接认证。因此首批工作
从批次 2 的 Agent 接线开始，不重复搭建服务，也不将服务端可投递等同于历史链路可用。
以下是待实现及验收要求，未提交的代码只能作为实现输入。

| 顺序 | 代码范围与具体交付 | 必须通过的验证 |
| --- | --- | --- |
| 2.1 固定恢复契约 | `history_session.py` 契约、会话仓储及投递端：请求携带总单元数、服务端已完成游标；明确请求退出投递集合的消息 | 游标不越界；移除先于新增，替换请求不产生第三个名额；移除仅取消路由资格，不授权删文件 |
| 2.2 Agent 专用客户端 | 新历史客户端及 `runtime.py` 生命周期：认证、续连、独立心跳、有界消息队列和工作消费 | 采集或上传等待不阻塞心跳；旧连接 ACK 不更新新会话；重连沿用原请求/许可；错设备、错计划和越界单元在原生调用前被拒绝 |
| 2.3 持久化请求与单元目录 | `journal.py`、`native_unit_artifact.py` 及 spool 管理：保存原请求身份、计划和文件引用；单元目录独立于旧 reset | 重启复用已验证字节；临时、孤儿及失败文件计入总物理预算；sweeper 不删除活跃引用；空间未知或不足时暂停采集 |
| 2.4 子进程单元执行 | `historical_worker.py` 和 `collection_execution.py`：通过有界 IPC 执行一个获准单元，保持原生调用隔离和共用锁 | START 被 Worker 接受后才进入原生调用；原请求总预算不因拆分重置；取消等待真实执行退出；STARTED 但缺本地授权证据时阻塞，不重新采集 |
| 2.5 组装、续传与证明 | `runtime.py` 上传路径：校验并回放单元文件，生成原请求的规范序列及 manifest，沿用原上传 ID | 仅服务端确认全部单元 FINISH 后组装；bars 保持 period/code/time 顺序；上传确认丢失可对账续传；一个请求贯通写入、回读及证明 |
| 2.6 故障收敛与接管 | 请求错误分类、会话 supervisor、QoS 及旧消费路径 | 确认丢失不重采；未知原生结果明确阻塞；确定失败与全局依赖故障分开；全部入口迁入批次 3 后删除旧派发及消费 |

恢复协议必须区分三个确认点：START 的 ACCEPTED 才允许原生执行；文件完整发布并绑定
journal 才发送 FINISH；服务端持久化证明才表示数据交付完成。HTTP 202、单元 FINISH
和上传完成均不得替代最终证明。已上传结果的本地清理还需确认服务端的持久化接收语义、
引用和保留期，不能仅凭请求从 WS 投递列表消失就删除唯一副本。

原生失败路径须先定义可验证的结果：能够证明调用未进入或已退出的失败，按明确的终态
协议收敛；无法证明是否仍执行或是否已产生结果时，保留 STARTED 并暴露恢复条件。
不能只增加 `fail` 调用便释放全局原生名额，也不能把所有确定失败永久留在未知状态。

QoS 改用独立历史连接健康作为传输条件，同时保留真实交易命令、回报积压、快照新鲜度、
XTData 和实时流的保护。控制连接中断后的采集资格按这些实际事实判定，不能仅删除
认证检查就宣称隔离完成。实际业务 API 停止后的连续性仍属于隔离环境运行验收。

首批验收按“真实本地 journal/文件 + 本地 HTTP/WS + 临时测试库 + 原生替身”连接整链，
在 START 确认前后、文件发布与 journal 绑定之间、FINISH 确认前后和上传确认前后注入断开。
断开后核对原请求/许可 ID、原生调用次数、文件摘要、计划游标、公平计数和最终证明；
另测服务端 STARTED 而本地 journal 丢失、文件损坏、磁盘预算耗尽及两请求轮转。
通过后扩展批次 3 的所有采集类别，再按批次 4—7 推进；不以首个 bars 请求通过结束整改。

### 1.3 下一实现批：确定失败收敛与历史运行时接管

本批先完成 2.6 的故障收敛，再启用采集会话。当前 `runtime.py` 已启动独立的上传恢复
supervisor，但采集仍由控制会话的 `_market_request_loop` 消费，历史 QoS 仍检查
`_control_session_authenticated`。准备本节时，ABORT 契约、服务端消费和迁移仍是
工作区草稿；后续实现和验证进展记在第 9 节。服务端收敛通过不能替代 Agent 停止证明
与失败恢复的整链验收。

**失败事实与状态规则**

| 现场事实 | Agent 行为 | Worker 收敛与恢复规则 |
| --- | --- | --- |
| 本次执行失败，原生调用已确认退出，且未发布可恢复的成功文件 | 先持久化原许可、单元身份及失败事实，再投递 ABORT | 同事务将许可置 ABORTED、原请求置 FAILED；不推进单元游标、不增加成功公平计数 |
| STARTED 后重启，本地缺少成功或停止证据 | 保留文件和 journal，报告结果未知 | 保留原许可占用并暴露恢复条件；超时、当前没有子进程句柄均不构成释放证据 |
| 成功文件已发布，journal 绑定或 FINISH 确认丢失 | 校验原文件、补绑定、重放原 FINISH | 幂等推进原单元，不重采、不改发 ABORT |
| ABORT 已落本地 journal，服务端确认丢失 | 按原许可重放原失败事实 | 重复同一事实无副作用；冲突身份、原因或已成功完成的许可拒绝覆盖 |
| XTData 等共享依赖不可用 | 单独记录依赖状态并暂停新采集；当前执行仍按停止证据处理 | 全局背压与请求终态分别处理，不能把队列中未执行任务全部标为失败 |

ABORT 携带原 `CollectionUnit`、`native_exit=CONFIRMED_STOPPED` 和有限错误码。
该字段是 Agent 对已验证本地事实的声明，服务端仍须校验设备、许可、单元及状态。
API 只持久化回执，只有当前租约 owner 的 Worker 可以推进状态。HTTP 接收不等于
Worker ACCEPTED。已上传、正在处理或已完成的请求不能被迟到 ABORT 改写。
ABORTED 后再次采集必须通过原请求的显式恢复规则，不在后台自动重开预算。

**实现顺序与交付范围**

1. contracts、Data API、receipt/permit store 和迁移：原子增加 ABORT；保留旧回执
   原始含义和幂等性，迁移校验状态/时间约束及单元唯一索引。仅在隔离测试库演练；
   存在终止证据时，降级迁移不得静默删除或改写这些事实。
2. `journal.py`、`collection_execution.py`、`collection_receipts.py`：本次采集失败
   必须在共用原生锁内完成迭代器关闭、子进程停止并等待退出，随后写不可变失败事实。
   停止失败保持未知；文件发布后绑定失败走成功文件恢复。恢复先检查已落盘 ABORT，
   不进入原生调用。失败确认不得删除尚未满足保留策略的证据。
3. `history_pipeline.py` 与 `history_session.py`：确定失败只隔离对应请求，保留其他
   请求的调度资格；每次重连重建会话路由、清除旧活跃集合，同时保留原请求目录、
   journal 和许可身份。依赖故障采用共享背压，不新增另一套自动重试预算。
4. `runtime.py`：装配专用采集 supervisor、独立健康与退避，退出时等待原生线程及
   子进程收尾；QoS 保留交易队列、回报、快照新鲜度和实时流约束。全部类别接入后，
   同一批切换删除旧控制面历史派发和消费，不允许新旧执行循环同时启动。

**本批最小验收矩阵**

| 注入点 | 必须核对的结果 |
| --- | --- |
| START 前拒绝、START 后确定失败 | 未获 ACCEPTED 不调用原生；已停止失败收敛且下一请求可获许可 |
| 文件发布后、journal 绑定前断开 | 重启复用原文件和摘要，原生调用次数不增加 |
| 停止后、失败 journal 提交前退出 | 缺持久化停止证据时保持未知，不凭时间推断停止 |
| 失败 journal 提交后、ABORT ACCEPTED 前断开 | 重放原 ABORT，游标与公平计数不增加，无重复采集 |
| Worker 消费时租约失效 | 请求、许可、回执处理结果一并回滚，旧 owner 无推进权 |
| 迟到/冲突回执与已上传请求 | 拒绝覆盖成功事实；重复相同回执幂等 |
| 坏任务、依赖中断、重连和退出 | 单项隔离与全局背压有区别；旧路由清空；退出后无仍运行的原生调用 |

先用临时 PostgreSQL、真实本地 SQLite/文件、本地 HTTP/WS 与原生替身完成组合验证，
记录原 ID、调用次数、文件摘要、许可状态、游标和公平计数。通过后再扩展所有采集
类别及业务读取迁移。Windows 原生执行、业务 API 停止后的连续性和原任务恢复仍须
单独取得运行证据；本批测试通过不解除 P5/P6 退出门。

是拆分前预期数，扫描索引区分子范围。诊断成功不会修改任务状态，也不证明全天覆盖。

### 3.2 有界查询

1. 在保留各标的精确范围的基础上增加整个分组的顶层半开时间条件。
2. 页大小 2000、分组最多 20 标的/10000 键；继续验证完整预期键集合。

4. 单组共享最多 32 节点、深度 8、60 秒的初始预算。预算覆盖分页、拆分和底层调用，

5. 单键/最小区间失败或预算耗尽，持久化 `DEPENDENCY_QUERY_CAPACITY_BLOCKED`。
   对连接异常使用阶段重试预算，不嵌套启动另一套重试。

对相同完整预期键比较修改前后结果，测试重复毫秒 Tick、分页边界、额外已有行、缺键、
空 reader、取消和拆分终止。正常查询不得因新增拆分逻辑无条件增加扫描。

### 3.3 分阶段恢复

将“内容校验→写入确认→回读→证明”拆成可恢复阶段。checkpoint 至少绑定
`request_id / attempt / manifest_hash / phase / block_index`；确定批次顺序，
只有目标写入确认后才提交该块 checkpoint。未知写入结果幂等重写当前块。

重试状态落 PG，初始最多 4 次执行（首次加 3 次重试），退避 5/30/120 秒，
总窗口 5 分钟；进程重启不刷新额度。确定性认证/配置/容量阻塞立即停止同操作。
读回失败保留已确认写入，恢复只重做失败回读。显式恢复保留原 ID 和历史 attempt，
新 attempt 必须记录操作者/原因；自动探针不得偷偷重新建立预算。

### 4.2 持久化设计

### 4.3 API 与租约

状态区分 `last_progress_at` 与 `observed_at`，给出阻塞原因、恢复条件和关联任务。

需求接收已改为 `POST /market-data/internal/v1/demands`，返回持久化 demand_id；
`GET /market-data/internal/v1/demands/{id}` 只读返回分区、来源、采集/交付关联和状态。

仍使用 `/requests/{id}`。`0066` 保存需求目录，分区与本环境来源生成稳定 ID，
未关联需求最多 5000 个，同 ID 再次提交不重开、不消耗名额。生产 Worker 持租约选择
在线来源并在同一事务建立采集任务及关联；离线保留原 ID，30 秒后再探测，不创建摄取
attempt，不更新实际进展时间。开发来源由服务配置固定为 REMOTE，只在同事务建立

已实现内部本地读取 `GET /market-data/internal/v1/history`：必填 instrument、period
（tick/1m/1d）、trading_date，page_size 默认 1000、最大 2000，after 是上一页返回的
UTC 存储时间。查询范围是上海交易日的半开区间，Tick 时间包含可逆 ordinal；校验每条
记录的范围、身份及严格递增。返回 records（Tick 深度采用存储层平铺字段）、next_after、
exhausted；非空短页仍继续探测，只有空页 exhausted=true。分页结束不等于覆盖证明，
此接口不触发补数、不转发远端。单次查询及连接池等待共享 10 秒预算，Arrow 结果累计
最多 4 MiB；API 仅一个在途查询，繁忙返回 429，查询失败返回脱敏 503，不内部重试。
API 与持久化回读各分配一路；统一启动必须固定一个 Data API 进程，服务总预算仍须在

端点路径和 DTO 在 P2 定稿并同批更新调用方，不保留旧新两套调度语义。

均带有效 owner 条件。Influx 无 PG 事务 fence，因此失租后停止派发新写入、取消在途工作，

epoch 及已执行单元 journal，拒绝旧许可。实时 Redis 通知只用于唤醒。

单元文件完整发布并绑定 journal 后才允许发送 FINISH；FINISH 确认丢失可用原许可恢复，
不因原启动有效期已过而重新采集。文件发布后、journal 绑定前退出也可完整校验后补绑定。
已有执行记录而文件缺失时返回 `COLLECTION_NATIVE_OUTCOME_UNKNOWN`；结果损坏或不同
许可试图接管同一执行时拒绝恢复，不以重采猜测原结果。连续取消仍等待原生线程退出后
释放共用锁；调用方须提供同一原生锁、有界采集调用、物理字节预算和可信确认回调。
这是历史接线用执行器，尚未替换现有历史子进程循环；受管理的单元目录/清理、
专用会话传输和 Worker 确认消费必须继续一起接入，当前运行路径还不能宣称已应用此保证。

回执链增加 `CollectionReceipt`、`CollectionCompletion` 和只读确认状态契约。
Data API 在 `/agent/market-data/collection/{permit_id}/receipts` 接收 START/FINISH，
GET 同路径追加事件名查询状态；每次使用独立历史 token，正文最多 4096 字节。
FINISH 必须携带与原许可一致的单元身份、文件摘要、字节数和记录数；这些是原生完成
事实，不是上传或持久化证明。相同许可/事件最多一条不可变回执，冲突重发返回 409。
HTTP 202 只表示已保存，状态仍可能是 PENDING，Agent 必须等待 Worker 的 ACCEPTED。

新增 `0071` 回执表，Worker 独立消费循环在同一 PG 事务内推进许可、计划游标、公平
计数和回执结果；摄取/回读等待不阻塞该循环。过期或无效 START 持久化为 REJECTED，
不反复消费；失租整体回滚，接管者可以处理旧 STARTED 许可的完整 FINISH。
Agent 的 `HistoryReceiptClient` 提供执行器的 START/FINISH 回调，确认等待包括取 token
在内都有截止时间，网络异常不新建许可/需求；恢复继续原事实。Agent 主循环尚未装配
该客户端。已有 Caddy 历史上传前缀覆盖回执路径，无新增公开端口。

`0072` 保存独立历史连接的 session ID、设备/用户、能力、心跳及令牌到期时间。
Data API `/ws/agent/history` 使用 `quantx.history.v1` 子协议和历史 token；初始认证冻结
能力声明，每次心跳重新验证令牌与设备。连接租约最多 15 秒且不超过令牌有效期，旧连接
